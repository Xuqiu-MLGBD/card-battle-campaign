> 用户 2026-10-02 指定的两篇：

> 2. 《拆文件不等于解耦：十五年前的三国杀网页如何长成一个规则引擎》（`dreampuf/sgs` 的 `ARCHITECTURE_EVOLUTION.md`）

## 一、文章一：拖拽是表现，出牌是规则

**一句话**：把 CardView 从规则里解放出来。作者的原话是「第一版拖拽逻辑写在 CardView 里，加了冻结、复制、临时费用、随机目标和服务端校验后，CardView 成了全项目最危险的类，一次 UI 重构甚至改坏了出牌费用」。

### 1.1 出牌意图要单独成一个接口

```ts
type PlayCardIntent = { cardInstanceId: string; targetId?: string; source: 'hand'|'created'|'discard' };
function validatePlay(intent, battle): { ok: true, effects } | { ok: false, reason }
```

UI **不直接扣费**，只提交意图。拖拽只是提交意图的一种方式（还有点击两段式、快捷键）。

**对我们的用法**：这正是联合派对《规则契约》§6.5 那条「退化的点击两段式与拖动共享同一个状态机」的上位写法 —— 把「怎么选中目标」和「能不能出」彻底分开。上游 `index.js` 现在是 `placeCardFunc()` 一个函数里同时干「碰撞检测 + 查牌 + 扣费 + 上场 + 播动画」，那就是文章批评的写法。

### 1.2 手上那张清单（每条都能当验收项）

| 要点 | 具体做法 | 我们现在的状态 |
|---|---|---|
| **手牌区是布局系统** | 手牌区自己知道最大张数、间距、扇形角度、拖拽占位、安全区；卡牌**不知道自己排第几** | 上游是 CSS 绝对定位 + `:nth-child` 逐条写死（styles.css 里 `.card:nth-child(1..10)` 各一段） |
| **目标选择用语义区域** | `TargetResolver` 按卡牌配置 + 释放位置返回目标；命中区是**输入容错**，不等于碰撞盒或图片边界（Boss 立绘很大但可选区可能只在身体中部） | 上游 `attack.js` 靠元素 `id` 判定，没有命中区概念 |
| **费用校验必须集中** | `PlayCardService(cardId, sourceZone, targetId, battle)`；UI 拖拽时可调**轻量预校验**做高亮，释放时再调**正式校验** | 上游费用判定散在 `checkForRequiredMana()`（画 UI）、`placeCardFunc()`（扣费）、`computerCardPlace()`（AI 自己判）三处 |
| **动画与结算排队** | 动作队列：锁输入 → 飞出 → 施法 → 应用效果 → 受击 → 进弃牌 → 刷新 → 解锁；每步有完成信号 | 上游用嵌套 `setTimeout` 串（`opponentTurn` 里三层）；加速/跳过会乱 |
| **规则不等动画** | 结算可以先算完，表现逐步播；切后台恢复时可以直接跳到终态 | 上游是「命中那一刻才结算」，方向恰好相反（联合派对 未完工清单 第 20 条也是这个） |
| **拖拽手感** | 拿起放大 + 抬层 + 脱离手牌布局；靠近合法目标高亮；回弹取消；**手机上拖拽对象略高于手指**（手指会挡） | 上游是原生的 `dragElement`，拖动时直接改 `absolute` 定位并**频繁改逻辑手牌** |
| **多点触控** | 一次只允许拖一张；第二根手指忽略或用于取消 | 上游没有限制 |
| **中断要收干净** | `pointercancel`、页面失焦、弹窗打开 → 取消拖拽并恢复手牌布局 | 上游没有 |
| **失败要可解释** | 费用不够 / 目标类型不对 / 状态禁止 / 回合不允许，**给不同提示**，不要一律弹回 | 上游只有 `alert("You've Lost!")` |
| **牌面显示规则来源** | 「基础 2 费，本回合 −1，敌方光环 +1，最终 2 费」；描述由模板 + 当前修正生成，不手写最终串 | 上游卡面文案是写死的字符串 |
| **动态描述别每帧重排** | 只在状态变化/抽牌/费用变化/语言切换时刷新（卡牌 UI 密度高，文本测量很贵） | 上游每次 `render` 整树重建 |
| **预览不越权** | 预览与结算**走同一个规则入口**；随机效果不给确定结果（给范围），复杂连锁只预览第一层 | 上游无预览 |
| **区域要可视化** | 抽牌堆/弃牌堆/消耗区/生成区都影响决策；每张牌的 zone 变化是**规则真相**，飞行动画只是表现 | 上游只有 `#playerDeck` 上的一个数字 |
| **洗牌记 seed** | 否则抽牌异常无法复盘 | 上游是 `Math.random()` 式全局过程 |
| **禁用路径测试** | 眩晕/回合结束/动画中/网络等待/弹窗 → **所有出牌入口共用同一把带 reason 的锁**；不能只禁拖拽（快捷键、双击还能出） | 上游无锁 |

### 1.3 最值得先做的三条

按「改动小、收益大」排：

1. **出牌意图接口**（`PlayCardIntent` + `validatePlay`）—— 让「能不能出」只有一个答案来源。
2. **带 reason 的操作锁** —— 一条 `canAct()`，拖拽/点击/快捷键/英雄技能全查它。这一条能一次消掉一大类「明明灰了还能点」的 bug。
3. **合法目标一次算好** —— 联合派对契约 §6.2 已经写了「非法目标必须在开始拖动时就全部变灰」，其实就是文章说的 `LegalAction` 投影。把这份集合也喂给 AI，UI 与 AI 就不可能漂移。

## 二、文章二：拆文件不等于解耦

**一句话**：旧版把复杂度藏在**调用顺序和共享对象**里，新版把它放进**类型、状态机、规则点和可检查的数据结构**里。文章给的判据只有三条：

1. 添加一种新内容时，需要修改多少个既有模块？
2. 一个模块能否只依赖显式输入，还是必须猜测全局对象正处于什么阶段？
3. 同一条规则在 UI、AI 和引擎中是否各自实现了一遍？

### 2.1 三段演进（对照我们的处境）

| 阶段 | 特征 | 我们的对应 |
|---|---|---|
| naive | `Card` 存牌名，规则在 `interpreter` 里按 `card.name` 分支；`Bout` 同时存玩家/牌堆/阶段/操作栈/响应队列；改一张牌要在目标选择、结算、AI、动画、映射表各加一个 `case` | **上游 `hearthstone-web` 就是这个形态**：`placeCardFunc()` 里查牌名、`computerCardPlace()` 里 AI 按费用挑牌、`attack.js` 里判胜负、`card_effects.js` 里按牌名分支 |
| 物理拆分 | 拆成 7 个文件、2900 行；**依赖方向没变**，解释器直接改对象、AI 直接读解释器栈、动画依赖字符串事件 | 我们加的 `campaign.js` 有同款味道：AI 难度靠**包装** `computerCardPlace()` 按费用挑牌 —— 那是「AI 里又写了一遍出牌规则」的雏形，得盯着 |
| Core | 卡牌声明意图、规则补上下文、只有引擎改状态；消费者只看快照/合法动作/领域事件 | **联合派对的擂台式契约已经走了大半**：`vocab.js` 能力词表 + `keywords.json`/`effects.json` 用 `impl` 注册名与代码挂钩、`ops.js` 操作派发、时机枚举、认不出的条目回退 AI 裁决、卡组包可移植 |

### 2.2 六个可直接采纳的机制

**① 上下文属于规则集，不属于卡牌**

「杀」的定义只写「对攻击范围内一名其他角色造成伤害」，它**不调用 `askJink()`**；「要求出闪」是标准包里的一条 `resolutionRules`，按 tag `response:slash` 匹配。好处：另一个内容包注册一张带同样 tag 的新「杀」，**自动进入同一条闪响应管线**。

> 对联合派对：`keywords.json` / `effects.json` 就是这份「规则集」的雏形。要补的是**因果方向** —— 卡牌不要主动去问「有没有嘲讽」，而是声明自己的操作与 tag，由规则侧组合。（他们的 `flags.taunt` + `targetable()` 已经是这个方向了。）

**② RuleBus 要限制入口，不是随便广播**

作者明确反对「一看到耦合就加 EventBus，最后只是把直接调用换成难以追踪的字符串广播」。他们的 `RuleBus` 只有六个语义点（`card-declared` / `target-confirmed` / `delayed-card-resolving` / `before-effect` / `after-event` / `legal-actions`），是**确定性的规则组合器**，不是消息总线。

> 对联合派对：他们的时机枚举（16 个）比六个更宽，但方向一致。要注意的是别让它长成「谁都能挂谁都能改」的广播网。

**③ 决策必须是状态，不能是回调**

> 「卡牌游戏最难保存的不是玩家血量，而是『刚才运行到哪里』。」

未完成的结算要显式进状态：`stack` / `triggerQueue` / `effectPlans` / `pendingDecision`。状态里存 plan ID；`assertGameState()` 甚至**拒绝**嵌在快照里的运行时 continuation。配合 `seed` / `rngState` / `revision` / `eventLog`，保存、恢复、复盘、确定性测试才有同一个基础。

> 对联合派对：他们的回合制是同步结算、拖拽期间用 `S.src` / `S.targets` 当临时状态，**没有 PendingDecision 这一层**。真要做「中途存档 / 复盘 / 回放」，这一层是绕不过去的。受 MMD 沙盒的 `sdk.save` 限制（10 个键），建议至少把 `seed + 操作日志` 存起来。

**④ Command / Effect / Event 三段式**

| 概念 | 回答 | 例子 |
|---|---|---|
| Command | 玩家/AI **想**做什么 | `use-card` / `respond-card` / `choose-cards` |
| Effect | 引擎**接下来**怎么改状态 | `damage` / `move-card` / `request-response` |
| Event | 状态**已经**发生什么 | `CardMoved` / `DamageApplied` / `DecisionRequested` |

关键推论：**动画完成不应该决定伤害是否生效**。伤害先在 Core 里发生，`DamageApplied` 只是通知 UI 怎么演；动画失败也不能让规则停在半路。上游恰好相反（`attack.js` 在 `setTimeout` 里判血、判胜负），所以「点击加速」这类改动很容易把结算顺序改坏。

**⑤ UI 与 AI 必须共享同一份合法动作**

旧版有两套合法性（UI 先让点、再调 `select_card()`；AI 自己按牌名和权重推），稍有漂移就出现两类典型故障：「玩家选中牌以后才发现不能用」，以及「AI 构造了 UI 从未考虑过的上下文，解释器在 `opt.target` 上崩溃」。

新版：`getLegalActions()` 是**唯一**动作来源；UI 不重新判断规则，只把 legal actions 按手牌归组：

```ts
{ cardId, enabled: uses.length > 0 || response !== undefined, targetSets: uses.map(a => a.targetIds) }
```

这直接对应两个界面行为：**没有任何合法动作的牌在选中之前就灰掉**；**选中一张牌后，所有合法 `targetSets` 里的英雄统一高亮**。AI 也只读同一份，只负责给动作**打分**，不负责发明动作。

> 这是整篇里对我们最有用的一条。它同时解决「灰了还能点」和「AI 行为诡异」两个问题，而且**不需要重写引擎**——只要把「合法动作」抽成一个纯函数，UI 与 AI 都调它。

**⑥ 逃生舱要比直接改状态更窄**

不是所有卡都能写成一串静态原子效果（「五谷丰登」要多次暂停/恢复）。他们的做法：复杂协议写成 `WorkflowDefinition`，但**只能**读不可变快照、返回通用 `EffectDraft[]`、请求一个 `WorkflowDecision`、保存可序列化 `resumeData` —— **workflow 不能直接改引擎**。

> 「数据驱动不是追求百分之百 JSON，而是控制特例代码能拿到的权限。」—— 这句话对联合派对同样成立：他们的 `custom` 操作（引擎不实现、回退 AI 裁决）就是同一个思路，只是权限边界还可以再收紧。

### 2.3 如果从零做，先固定这八件事

文章列的八条，按我们的体量删减后，**真正需要现在就定的是前四条**：

1. **稳定 ID 与区域模型** —— 实体牌有 instance ID，规则定义有 definition ID；手牌/牌堆/弃牌/场上都是显式 zone，任何时刻一张实体牌只在一个 zone。这是**移动动画、隐藏信息、偷牌、回放、一致性校验**共同依赖的地基。
2. **可序列化、可校验的唯一状态** —— 状态里不能藏 DOM、函数、Promise。每次命令后可跑 invariant（所有 card ID 有定义、每张牌恰好在一个 zone、revision 单调递增……）。
3. **显式时机与确定顺序** —— 时机是有限集合，并定义优先级、座次顺序、可选与强制、一次与重复、取消与替换。**不要让卡牌 A 直接调用技能 B。**
4. **唯一合法动作生成器** —— UI、AI、测试都消费同一份。
5. 决策是可恢复状态 / 6. 版本化内容注册 / 7. 受控的特例出口 / 8. Command-Effect-Event —— 我们量级小，可以先记着，等真要做存档与复盘再上。

### 2.4 最后那把尺子

> **为了实现一张新卡，是否必须修改一张无关的旧卡、AI 的牌名分支、UI 的合法性判断，或者引擎中的内容名称 switch？**
> 如果答案是「是」，先别急着加 case，应该看看缺的是不是一个通用语义、时机、Effect 或 Decision。

## 三、落到我们身上：这份案子接下来该定什么

两篇文章合起来指向同一件事 —— **把「卡牌」和「上下文」分开，并且让合法性只有一个来源**。

对照这个案子的现状（`关卡挑战版/` 是上游 naive 结构的直接继承，`campaign.js` 只包了 AI 与胜负），我建议按这个顺序讨论与推进：

| 顺序 | 要定的事 | 为什么是它 | 参考 |
|---|---|---|---|
| 1 | **合法动作的唯一出口** | 一次解决「灰了还能点」+「AI 行为诡异」+「UI 与 AI 漂移」，且不用重写引擎 | 文章二 §UI 与 AI 必须共享同一份合法动作 |
| 2 | **出牌意图接口** `<br>`（`PlayCardIntent` + `validatePlay`） | 让拖拽/点击/快捷键都只是「提交意图」，规则只有一份 | 文章一 §一个出牌意图接口 |
| 3 | **带 reason 的操作锁** | 禁用路径测试的前提；也是「失败要可解释」的落地 | 文章一 §上线前检查清单 |
| 4 | **区域模型（zone）** | 卡组/弃牌/消耗区可视化、抽弃洗都走它；也是回放的地基 | 文章一 §卡组和弃牌堆也要可视化 · 文章二 §1 |
| 5 | **UI 配布与动效**（我们自己的） | 用户已把炉石美术全部摘掉，正是为这一步留的位置 | 文章一 §手牌区是布局系统 · §拖拽手感 |
| 6 | **随机 seed + 操作日志** | 复盘与确定性测试的起点；不必一次做到 PendingDecision | 文章二 §决策必须成为状态 |

**不用照搬的**：sgs 的 Core 过万行，我们是 MMD 单卡、单条规则还要卡 18000 UTF-16 的门禁。要取的是**边界**（谁是唯一合法来源、谁有权改状态、特例能拿到多大权限），不是它的实现体量。
