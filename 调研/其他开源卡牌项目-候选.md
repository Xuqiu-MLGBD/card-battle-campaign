## 二、A 方案：`piovium/genius-invokation` —— 它的机制正是你要的

★97 · **AGPL-3.0** · TypeScript · 1120 个文件 · 最后推送 **2026-10-01**（就是昨天）· 在线试玩 <https://standalone.piovium.org>

这是原神「七圣召唤」的模拟器（`piovium` = 八重堂）。七圣召唤本身是**炉石式**的：角色站场、技能、能量、骰子当费用、召唤物、装备。README 自称「核心实现了目前最接近官方的结算规则」。

### 2.1 决定性的证据：引擎吐的是「一串变化」，不是「结果」

`proto/notification.proto` 全文只有两句：

```proto
message Notification {
  State state = 1;
  repeated ExposedMutation mutation = 2;   // ← 一串「发生了什么变化」
}
```

引擎和 UI 之间靠 `proto/` 里那套 `action / mutation / notification / state / rpc` 通信。**UI 拿到的不是最终画面，而是一个状态 + 一串按顺序发生的变化** —— 这就是「有过程」的前提：有了一串变化，UI 才可能一条一条演出来。

### 2.2 演出机制就在这一个文件里：`packages/web-ui-core/src/queue_manager.ts`

它是一段**串行任务队列**，文件头上的注释直接写了用途：

> 「串行任务队列，每个任务可附带元数据（**如动画所属的行动轮次**），并支持基于元数据的等待查询。」

```ts
export class QueueManager<M extends {}> {
  push<T>(task: Task<T>, meta?: M): Promise<T>          // 压一条动画进去，附上它属于哪个行动轮次
  pending(): M[]                                        // 当前正在跑 + 排队的那些元数据
  waitUntilNone(matches: (meta: M) => boolean): Promise<void>  // 等某一轮次的动画全部播完
  drain(): Promise<void>
  private async processQueue() { /* while 队列非空：await 每一条 */ }
}
```

配套的 `ui_state.ts` + `primitives/key_with_animation.ts` 里还有一条很关键的保护：

```ts
prev.setItem((prev) => (!isForceUpdate && prev.uiState.isAnimating) ? prev : item)
```

**动画正在播的时候，新状态不允许覆盖它** —— 所以不会出现「动画演到一半被后一条变化打断」。这正是「先亮牌、再结算」能成立的原因。

### 2.3 表现层也是齐的

`web-ui-core/src/components/` 下有一整套：`PlayingCard` `Card` `Entity` `Damage` `NotificationBox` `Reaction` `RoundAndPhaseNotification` `SwitchHandsView` `SelectCardView` `HistoryViewer` `MiniSpecialView` `SkillButtonGroup` `DicePanel` `TogglingDiceView`…… 另有 `packages/detail-log-viewer`（结算细节日志）、`packages/state-editor`（状态编辑器）、`packages/test`（测试）、以及 C/C++/Python/C# 的跨语言绑定。

### 2.4 为什么只能借架构、不能搬代码

1. **AGPL-3.0** —— 传染性强，且带网络服务条款。我们这份是要放进 MMD 角色卡里分发的，代价很实在。
2. **它是七圣召唤专用的**：骰子、角色技能、召唤物、元素反应都不是通用 TCG 概念，`packages/data` 里全是原神卡牌定义。当通用引擎用会处处别扭。
3. **pnpm monorepo，要构建**：`packages/` 下十几个包 + `proto/` 要生成代码。而 MMD 沙盒**没有构建步骤**，单条规则还卡 18000 UTF-16（详见 `MMD-适配说明.md`）。它的体量比我们现在这份大一个数量级。

**所以它对我们最大的价值是「示范」**：`Notification = State + Mutation[]` 这一对边界，加上一个串行的动画队列 + `isAnimating` 保护 —— 这三样凑起来就是你要的东西，而且**加起来不到 100 行**。

## 四、B 方案：在当前基座上实现「AI 回合逐步演出」

你描述的两个动作，拆开看是这样：

### 4.1 出牌：手牌 → 箭头指向目标 → 亮牌 → 效果生效 → 进弃牌

上游其实已经有**一半**基础设施了：

- `#svg` + `#svgpath` 那套箭头是现成的（`attack.js` 里用 `setAttribute('d', 'M... L...')` 画线，玩家拖拽打人就是用它）。`ai.js` 空文件、`anim.js` 在上游里没有。
- 我们的 `ours.css` 现在把 `placeCardAnim` **留着没停** —— 出牌落位那一下还在。
- 缺的是：**把「AI 出牌」从「直接 append 到场上」改成一段可 await 的序列**。

伪代码（这就是 `QueueManager` 的思想，不需要引入任何依赖）：

```js
// 每一条动画都是一个返回 Promise 的任务，串行播放
const queue = [];
let running = false;
function push(task, meta) { /* ... 与 piovium 的 QueueManager 同构 ... */ }

async function aiPlayCard(card, handIndex, targetUid) {
  await drawArrowFromHandTo(handIndex, targetUid);   // ① 手牌引箭头到目标
  await revealCard(card);                            // ② 把 bot 要打的牌亮出来
  await push(() => applyEffect(card, targetUid));    // ③ 让效果生效（这才是改状态）
  await moveToDiscard(card);                         // ④ 进弃牌堆
}
```

### 4.2 随从攻击：箭头指向目标 → 移动到目标上方 → 移回来

```js
async function aiAttack(attackerUid, targetUid) {
  await drawArrow(attackerUid, targetUid);            // ① 箭头
  await moveAbove(attackerUid, targetUid);            // ② 冲到目标上方
  await applyDamage(attackerUid, targetUid);          // ③ 结算（可能致死）
  await moveBack(attackerUid);                        // ④ 移回原位
}
```

### 4.3 为什么这条比换项目划算

- **不用换基座**：上游的箭头、卡面 DOM、伤害数字气泡（`#computerdamagecontainer`）都现成。
- **不用引入依赖**：队列就是 `Promise` 串行，没有新库。
- **符合你已经认可的方向**：你先前让我读的两篇文章，正好一边讲「动画与结算要排队、每个动作有完成信号、规则不等动画」，一边讲「决策要成为可恢复的状态」。这条实现正好把两句话落到同一个地方。
- **代价**：上游现在是「命中那一刻才结算」（`attack.js` 在 `setTimeout` 里判血判胜负），要改成「结算先算、动画按队列播」，得动到 AI 那条路径。这是这一轮唯一需要动上游行为的地方。
