## 1. 目标与非目标

**要做的**：一个可复用的**演出管线** —— 引擎把「发生了什么」写成一条条**变化**，管线按顺序一条条**演出来**；玩家看到的每一步都是真的发生过的那一步。

**明确不做**：

| 不做 | 为什么 |
|---|---|
| 不引入动画库（GSAP / tween.js / anime.js） | 先用原生 `transform` + `transition` / `Web Animations API` 做到位；不够再说。依赖越少，将来压进 MMD 越容易 |
| 不让动画决定规则 | 状态先算完，演出只是**回放**。见 §3.3 |
| 不在这一轮改玩法/数值 | 这一轮只做「呈现层」，规则维持原样 |
| 不搬 `piovium` 的代码 | 它是 AGPL-3.0。只借它的**边界划分**（见 §3.2），代码全部自己写 |

## 2. 现状盘点：我们手上已经有什么

先摸清家底，方案才不会悬空。以下都是**当前 `关卡挑战版/` 里实打实存在**的东西：

| 现成件 | 在哪 | 能直接拿来演什么 |
|---|---|---|
| **SVG 箭头** | `index.html` 的 `#svg` + `#svgpath`；`attack.js` 里 `svgpath.setAttribute('d', 'M… L…')` | 玩家的拖拽瞄准**已经在用它画直线**。AI 的「手牌→目标」「单位→目标」两条箭头可以直接复用同一个元素 |
| **箭头光标三件套** | `#innercursor` / `#outercursor` / `#arrowcursor` | 箭头头部（三角形）与拖尾的现成做法 |
| **伤害数字气泡** | `#computerdamagecontainer` / `#playerdamagecontainer` + `#…damagevalue` | 「-3」飘字已经能用了，只是现在由 `attack.js` 在结算时点亮 |
| **出牌落位动画** | `@keyframes placeCardAnim`（`animations.css`） | 我们剥炉石美术时**刻意留着没停**的动效之一 |
| **卡面 DOM** | `.card`（手牌）· `.cardinplay.player-cardinplay`（我方场上）· `.cardinplay.computer-cardinplay`（敌方场上）· `#playerhero` / `#opposinghero`（英雄）· `#playerheropower`（技能） | 所有可被指向的目标实体，都有稳定的 id / class |
| **卡的状态类** | `.canAttack` / `.hasTaunt` / 覆盖层置灰 | 「谁能动」「谁挡路」在 DOM 上已经能读出来 |
| **入队锁** | `#block`（半透明遮罩，`pointerEvents` 可切） | 「动画播放期间不许操作」的现成开关 |

**缺的三样**（这就是这一轮要补的）：

1. **一个串行播放队列** —— 现在 AI 是 `computerCardPlace()` 直接 `appendChild`，一步到位，没有中间过程。
2. **一个「变化」数据结构** —— 现在「发生了什么」只写在 DOM 上（掉血直接改 `innerText`），拿不到一份可回放的清单。
3. **一套位移动画** —— 现在没有任何「元素从 A 移到 B 再回来」的能力。

## 3. 核心设计

### 3.1 一句话

> **规则先把这一回合算完，产出一串「变化」；演出层再拿着这串变化，一条一条演出来。**
> 玩家点「结束回合」之后看到的每一个动作，都对应清单里的一条。

### 3.2 三个东西要分开（这是整份方案的地基）

| 概念 | 回答的问题 | 谁产出 | 谁消费 | 我们现在的状态 |
|---|---|---|---|---|
| **Command**（意图） | 玩家/AI **想**做什么 | 玩家输入 / AI 决策 | 规则 | `placeCardFunc` / `AI()` 里混着 |
| **Mutation**（变化） | 状态**刚发生了什么** | 规则结算完产出 | 演出队列、日志、将来的复盘 | **没有，这是要新建的** |
| **Presentation**（演出） | 这件事**看起来**怎么演 | 演出管线 | 玩家 | 散在 `setTimeout` 里 |

> 这个三分法是那篇三国杀架构文的核心（它叫 Command / Effect / Event），也是 `piovium` 的做法
> （它的 `Notification = State + repeated Mutation`）。
> **关键推论：动画完成与否，不决定伤害是否生效。** 伤害先在规则里发生，演出只是通知 UI 怎么表现。
> 我们现在的上游恰好相反 —— `attack.js` 是在 `setTimeout` 里判血、判胜负的，所以「动画中」和「结算中」是同一件事。**这是这一轮唯一必须动到规则路径的地方。**

### 3.3 为什么必须「先算完再演」

Phaser 那篇的原话是：*「不要指望规则结果依赖动画有没有播完」*，并且给了理由：动画要能加速、跳过、切后台恢复。
如果我们继续「演到那一帧才结算」，那么：

- 加速 = 改结算时机 → 数值可能对不上；
- 切后台 = 动画暂停 → 结算也卡住；
- 跳过 = 得把剩下的效果补算一遍。

而「先算完再演」下，这些全部变成纯呈现问题。

### 3.4 串行播放队列（约 60 行，无依赖）

`piovium` 用一个 `QueueManager` 做这件事，注释写得很准：「串行任务队列，每个任务可附带元数据（**如动画所属的行动轮次**）」。我们照这个结构自己写一个 —— 只要 `Promise`，不要库：

```js
// 演出管线：一条一条按顺序播，每条都是一个返回 Promise 的任务
const queue = [];
let running = false;
let currentMeta = null;

function push(task, meta) {                  // meta 例：{ turn: 3, side: 'enemy' }
  return new Promise((resolve, reject) => {
    queue.push({ task, meta, resolve, reject });
    if (!running) run();
  });
}

async function run() {
  running = true;
  lockInput(true);                            // 播放期间锁输入（见 §3.7）
  while (queue.length) {
    const e = queue.shift();
    currentMeta = e.meta;
    try { e.resolve(await e.task()); } catch (err) { e.reject(err); }
    currentMeta = null;
  }
  running = false;
  lockInput(false);
  onIdle();
}

// 「等某一方的动画全部播完」—— 切回合、切会话时要等
function waitUntilNone(matches) { /* ... 与 piovium 的 waitUntilNone 同构 ... */ }
```

### 3.5 「动画中不许被覆盖」

`piovium` 的 `key_with_animation.ts` 里有一条保护：*动画正在播的时候，新状态不允许覆盖它*。我们同样需要，否则「亮牌」亮到一半就被下一条变化改掉了。做法是在实体上挂一个 `animating` 标记，`render()` 遇到它跳过该实体。

### 3.6 位移一律用 `transform`，不动布局

这一点是从我们现有 DOM 结构推出来的、不是抄来的：

- 场上随从是 `.cardinplay { float: left }` 排在 `.board--player` 里的 —— **它们是流内元素**。
- 所以「冲到目标上方再回来」**绝不能改 `left/top` 或 `margin`**，那会把同一排的其它随从挤走。
- 正确做法：`transform: translate(dx, dy)` + `transition`。`transform` 不参与布局，动完回到原位，DOM 顺序与流不变 —— 这同时满足「动画不改逻辑状态」。

同理，抬高层级用 `z-index`（或 `isolation`），不要用会打断层叠的 `filter`/`opacity` 组合。

### 3.7 操作锁（一条锁，所有入口共用）

Phaser 那篇专门点了这个：*「不要只禁用拖拽，快捷键或双击仍然能出牌」*，并且要求**锁要带 reason**。
我们的锁要有三个状态：

| 状态 | 触发 | 表现 |
|---|---|---|
| `ANIMATING` | 演出队列正在播 | 输入全锁；允许「点击加速 / 再点跳过」 |
| `RESOLVING` | 规则正在算（理论上极短） | 输入全锁，不给加速 |
| `WAITING_REMOTE` | 等 AI 回话（走消息通道时） | 输入全锁，给「等待中」提示 |

`lockInput(reason)` 只认 reason，UI 上任何可点入口（手牌、场上随从、英雄、技能、结束回合）**都先问它**。

### 3.8 中断要收干净

Phaser 那篇列了三种必须处理的中断，我们都要接：`pointercancel`、**页面失焦**、弹窗打开。
对应到队列：**当前任务要能被 cancel**，且 cancel 之后状态必须是「这一条演完/没演完」二选一，不能半途。
最稳的做法是：每个动画任务都用 `Web Animations API` 拿到一个 `Animation` 对象，cancel 时 `finish()`（直接跳到终态）而不是 `cancel()`（回到起点）—— 这样补一个「立刻到终态」就收干净了。

## 4. 两个目标动作的时序（你描述的那两个）

### 4.1 AI 出牌

```
① 手牌 → 目标
   从对手手牌区那一叠里取一张（背面），沿贝塞尔曲线飞到目标上方，尾部拖一条箭头
   —— 复用 #svg / #svgpath，不用新建箭头层

② 亮牌
   卡面翻到正面（就是那张真的会被打出的卡），停 0.4–0.6 秒让人看清

③ 生效
   ★ 这一条只是「回放」已经算好的结果：掉血 / 加 buff / 召唤
   （伤害数字气泡 #computerdamagevalue 在这里点亮）

④ 进弃牌
   卡面缩小飞向对手牌堆，牌堆数字 +1
```

### 4.2 AI 单位攻击

```
① 箭头    攻击者 → 目标，画一条直线箭头并短暂停留
② 冲上去  transform: translate() 移到目标上方（约 0.18s）
③ 结算    伤害数字 + 可能的退场（退场用现有的移除逻辑）
④ 移回来  transform 回 (0,0)
```

> 这两段就是**变化清单的两个渲染器**。变化清单的形状见 §5 —— 它不认识「动画」，只认识
> 「谁对谁做了什么」。所以将来换一套演出（比如加个挥拳特效）不用碰规则。

## 5. 数据契约：变化清单

一条变化的形状（先定成最小集，够演这两段就行）：

```js
// Mutation —— 「状态刚发生了什么」
{ kind: 'card-played',   turn, side, card, target }          // 打出一张牌
{ kind: 'damage',        turn, side, source, target, amount, lethal }  // 造成伤害
{ kind: 'heal',          turn, side, source, target, amount }
{ kind: 'summon',        turn, side, card, slot }
{ kind: 'death',         turn, side, target }
{ kind: 'buff',          turn, side, target, atk, hp }
{ kind: 'draw',          turn, side, who, count }
{ kind: 'deck-change',   turn, side, who, delta }            // 牌堆数量变化
{ kind: 'turn-end',      turn, side }
```

**每一条都只写事实，不写表现**（没有「飞出」「闪烁」这类词）。演出层拿到 `kind` 自己决定怎么演 ——
这正是 Phaser 那篇说的「预览与结算走同一入口」「表现失败时 zone 仍要正确」的同一件事。

## 7. 与 Phaser 那篇的逐条对照

你让我参考那篇很重要，那我把它的每一条都落到具体模块上，省得只是「看过」：

| 那篇的要点 | 落到哪 |
|---|---|
| 出牌意图单独成接口，UI 不直接扣费 | `pipeline/mutations.js` 的输入就是意图（`{cardId, targetId, source}`） |
| 手牌区是布局系统，卡牌不知道自己排第几 | 飞行起点由 `.cards` 布局算，卡自己不存坐标 |
| 目标选择用语义区域（命中区 ≠ 碰撞盒） | 箭头终点按目标的 `target hit area` 算，不按图片边界 |
| 费用校验必须集中 | 不在这一轮范围（规则不动）；但锁（§3.7）先按「唯一入口」建好 |
| **动画与结算排队** | **§3.4 的队列** |
| **规则不等动画** | **§3.3** |
| 拖拽手感：拿起放大、抬层、脱离布局 | 用 `transform: scale()` + `z-index`，布局不动（§3.6） |
| 多点触控只允许一张 | 锁（§3.7）顺带解决 |
| 中断要收干净（pointercancel / 失焦 / 弹窗） | §3.8 |
| **失败要可解释**（费用不够/目标不对/状态禁止 给不同提示） | 锁的 reason 直接映射成提示文案 |
| 牌面显示规则来源（基础 2 费 −1 光环 +1） | 留到 UI 那一轮 |
| **预览与结算同一个入口** | 变化清单本身就是结算产出，预览读同一份 |
| 区域可可视化（抽牌堆/弃牌堆/消耗区） | 队列里的 `draw` / `deck-change` 自带数据，UI 那一轮接 |
| 洗牌记 seed | 不在这一轮；但它属于「可复盘」的前置，先记在案 |
| 禁用路径测试 | 锁的 reason 可直接断言，测试好写 |

## 8. 分期落实（每期都有可验收的产物）

| 期 | 做什么 | 验收 |
|---|---|---|
| **1** | 队列 + 锁 + 变化清单（只接「伤害」一种变化），把 AI 单位攻击改成 §4.2 那段 | 敌方能「箭头→冲上去→飘字→移回」地打完一回合，且伤害数字与不演时**完全一致** |
| **2** | 接「出牌」：手牌→箭头→亮牌→生效→进弃牌 | 敌方每出一张牌都能看见是**哪一张**、打**谁** |
| **3** | 加速 / 跳过 / 失焦恢复 | 连点跳过不丢结算；切后台回来状态正确 |
| **4** | 失败原因提示 + 锁的可视化（为什么不能点） | 每个不可点都能说出理由 |
| **5** | 变化清单落成可导出的日志（为复盘/seed 铺路） | 能导出一回合的操作+效果序列 |
