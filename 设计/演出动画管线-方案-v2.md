## 一、先回答「那篇文章是怎么说的」

你指的那段原文如下（Phaser 卡牌拖拽那篇，"出牌动画和结算要排队" 一节）：

> 可以把出牌过程拆成**动作队列**：锁输入、卡牌飞出、播放施法、应用效果、播放受击、移动到弃牌区、刷新 UI、解锁输入。**每个动作有完成信号**。这样动画速度变化、跳过和回放都更可控。
>
> 结算也要**区分规则和表现**。**规则可以瞬间计算出敌人掉血和状态变化，表现按队列逐步播放**。若表现过程中玩家切后台，恢复时可以选择继续动画或直接应用最终状态。**不要让规则结果依赖动画是否完整播完。**

它还有一句配套的（"拖拽手感" 一节）：

> 拖拽过程中**不要频繁修改逻辑手牌**。逻辑手牌在确认出牌前不变，手牌区只显示一个临时占位。

三句话拼起来就是你要的那个顺序：**① 规则瞬间算完 → ② 得到一份「变更清单」 → ③ 按清单顺序播动画，每条播完再走下一条。**
动画只负责让玩家看见，**能不能看见不影响结果**。

（同一条边界，那篇三国杀架构文里叫 Command / Effect / Event：*「动画完成不应该决定伤害是否生效」*。）

## 三、三层分开（整套设计的地基）

| 层 | 回答 | 产出 | 谁写 |
|---|---|---|---|
| **计划 Plan** | 这一回合敌方**想做**哪些事 | `Action[]` | AI 规划器 |
| **结算 Resolve** | 每件事**实际**造成什么 | 每条 Action 挂上 `Mutation[]` | 规则（纯数据运算） |
| **演出 Present** | 每件事**看起来**怎么演 | 一段可 `await` 的动画 | 队列 + 配方 |

**关键顺序：计划全部产出 → 结算全部算完 → 才开始演出。** 这正是文章那句「规则可以瞬间计算出敌人掉血和状态变化，表现按队列逐步播放」。

为什么非要先算完，而不是「演到那一帧才结算」：文章给了三条理由，我们这里一一对应：

| 文章的理由 | 如果我们边演边算会怎样 |
|---|---|
| 动画可以**加速** | 加速 = 改结算时机 → 数值可能对不上 |
| 动画可以**跳过** | 跳过 = 得把剩余效果补算一遍，极易漏 |
| **切后台**恢复 | 动画暂停 → 结算跟着卡死 |

还有一条只有「先算完」才成立的好处：**计划阶段就能发现「这条做完之后那个单位已经死了」**，从而把它后面的动作直接作废。边演边算做不到这点 —— 你演到一半才发现施法者已经没了。

## 四、动作词汇表（把 9 条写成同构数据）

> **本节 2026-10-02 晚按用户口径重写。** 用户的原话：
> *「增益和减益不是重点，**重点是谁对谁**。一定要有清晰的关系，**来源**是从手牌还是从场上的某个单位，
> **目标**是哪个单位，是**角色、场地**（场上最多仅有 5 个角色部署位，每个部署位有其虚线轮廓，
> 场地卡可以移植到虚线轮廓中，给这单个部署位附加效果）**还是玩家**，是**友方的单位还是敌方的单位**，
> **切忌把场上的单位全部算做一个阵营**，bot 和玩家要区分开来。」*
>
> 所以这一节的核心不是「有哪些动作」，而是**每一条引用都必须把「哪一侧」写死**。

### 4.1 铁律：任何一个引用都必须带 `side`

```js
// ❌ 错的写法：把场上单位当成一个大阵营
{ kind: 'buff', target: 'allUnits' }
{ kind: 'attack', source: 'strongest', target: 'weakest' }

// ✅ 对的写法：每一次引用都指名「哪一侧的哪一个」
{ kind: 'buff',   to: { side: 'enemy', kind: 'unit', uid: 'e2' } }
{ kind: 'attack', from: { side: 'enemy', kind: 'unit', uid: 'e1' },
                  to:   { side: 'player', kind: 'unit', uid: 'p3' } }
```

**`side` 只有两个取值：`'enemy'`（bot）与 `'player'`（玩家）。**
绝不允许出现「不写 side 就是自己人」或「场上单位统一算一方」这种写法 ——
那正是「增益给错了人、攻击打错了边」这类 bug 的温床。**两个阵营从数据层就分开。**

### 4.2 一条 Action 的完整形状

```js
{
  verb: 'attack' | 'buff' | 'debuff' | 'deploy' | 'summon' | 'draw',
  from: Ref,          // 谁发起（draw 的 from 是牌堆）
  to:   Ref | null,   // 对谁（draw 没有 to）
  delta?: {...},      // 数值变化（buff/debuff 用；attack 的伤害由规则算）
}

// Ref —— 一个引用，三件事说全：哪一侧 / 什么形态 / 具体是哪个
{
  side: 'enemy' | 'player',        // ★ 必填，绝不留空
  kind: 'hand' | 'unit' | 'slot' | 'player' | 'deck',
  uid?: 'e1',                      // kind === 'unit' 时：该单位的稳定 id
  slot?: 0..4,                     // kind === 'slot' 时：第几个部署位（从 0 数）
  card?: {...},                    // kind === 'hand' 时：手牌里那一张
  // kind === 'player' 就是这一方的英雄本人；kind === 'deck' 是这一方的牌堆
}
```

**`kind` 的五个取值，正好对上用户说的三类目标：**

| kind | 是什么 | 用户的原话 |
|---|---|---|
| `unit` | 场上的一个**角色** | 「角色」 |
| `slot` | 一个**部署位**（也是场地位的挂点） | 「场地」 |
| `player` | 这一方的**玩家本人**（英雄） | 「玩家」 |
| `hand` | 这一方的**手牌**（作为来源用） | 「从手牌」 |
| `deck` | 这一方的**牌堆**（抽牌用） | — |

### 4.3 「场地」是一等目标，不是修饰

用户描述的场地是这样的：

> 场上最多 **5 个角色部署位**，每个部署位有其**虚线轮廓**；**场地卡可以放到虚线轮廓中**，
> 给**这单个部署位**附加效果。

所以：

- 部署位不是装饰，是**有编号的实体**（`slot: 0..4`），5 个/侧；
- **场地卡的 `to` 就是一个 `slot`**：`{ verb:'deploy', from:{side,kind:'hand',card}, to:{side, kind:'slot', slot:2} }`
- 场地卡挂上之后，**只改那一格上的角色** —— 换人上场照样吃这个效果（效果留在格上）；
- 所以每个 `unit` 引用其实隐含「它在哪一格」，我会在状态里给每个单位记 `slot`。

**这一条对演出有直接影响**：场地卡的箭头**指向格子**，不是指向角色；
落点高亮的是**格子轮廓**，不是角色卡。这和角色卡拖入格子的反馈是同一套（都用 `.hs-slot`），
只是场地卡挂在格子**上方那条窄槽**（`ours.css` 里每个 `.hs-slot::before` 画的那条）。

### 4.4 用新形状重写你列的 9 条

```js
// ① 抽牌
{ verb:'draw',   from:{side:'enemy', kind:'deck'}, to:{side:'enemy', kind:'hand'} }

// ② 从手牌上场一个单位（进第 3 格）
{ verb:'deploy', from:{side:'enemy', kind:'hand', card:{...}},
                 to:  {side:'enemy', kind:'slot', slot:2} }

// ③ 通过场上单位的效果上场一个新单位（e1 召出一个，进第 5 格）
{ verb:'summon', from:{side:'enemy', kind:'unit', uid:'e1'},
                 to:  {side:'enemy', kind:'slot', slot:4} }

// ④ 用手牌给**他**的单位加增益        —— 两侧都是 enemy
{ verb:'buff',   from:{side:'enemy', kind:'hand', card:{...}},
                 to:  {side:'enemy', kind:'unit', uid:'e2'}, delta:{atk:+2, hp:+2} }

// ⑤ 用手牌给**我**的单位施加减益      —— from 是 enemy，to 是 player
{ verb:'debuff', from:{side:'enemy', kind:'hand', card:{...}},
                 to:  {side:'player', kind:'unit', uid:'p1'}, delta:{atk:-2} }

// ⑥ 让他场上的单位给他场上的单位加增益 —— 两侧都是 enemy
{ verb:'buff',   from:{side:'enemy', kind:'unit', uid:'e1'},
                 to:  {side:'enemy', kind:'unit', uid:'e2'}, delta:{atk:+1} }

// ⑦ 让他场上的单位给我场上的单位减益   —— from enemy，to player
{ verb:'debuff', from:{side:'enemy', kind:'unit', uid:'e1'},
                 to:  {side:'player', kind:'unit', uid:'p1'}, delta:{atk:-1} }

// ⑧ 让他场上的单位向我场上的单位攻击   —— from enemy，to player
{ verb:'attack', from:{side:'enemy', kind:'unit', uid:'e1'},
                 to:  {side:'player', kind:'unit', uid:'p1'} }

// ⑨ 让他场上的单位向我这个玩家攻击     —— to 的 kind 是 player
{ verb:'attack', from:{side:'enemy', kind:'unit', uid:'e1'},
                 to:  {side:'player', kind:'player'} }
```

**注意 ④ 与 ⑥、⑤ 与 ⑦ 的差别只在 `from.kind`**（`hand` 还是 `unit`）——
它们的目标侧完全一样。所以「给我方减益」这件事，无论来自手牌还是来自某个单位，
**演出配方是同一条**，只是箭头起点不同。这正是把关系写清楚之后自动得到的好处。

**`delta` 是数据不是动作**：`{ atk:+2 }` / `{ atk:-1, hp:-1 }` / `{ keywords:['taunt'] }`。
增益与减益**是同一个动作**，只是符号不同 —— 所以配方表里它们是同一行。
（但**谁对谁**这条关系永远不能省。）

## 五、演出配方表（源形态 × 动作 → 怎么演）

这张表就是「9 条怎么实现」的答案。**看的是源形态，不是具体哪条**：

**落点由 `to.kind` 决定高亮什么**（这一列是 v2.1 加的，对应「目标可以是角色 / 场地 / 玩家」）：

| `to.kind` | 高亮的是 | 落点坐标取自 |
|---|---|---|
| `slot` | **格子的虚线轮廓**（`.hs-slot`） | `slotRect(side, i)` |
| `unit` | 那个角色卡，套`--hs-ok`绿框 | 该元素的 rect |
| `player` | 那一方的英雄区 | `#opposinghero` / `#playerhero` |

| 动作 | 源 = 手牌 | 源 = 场上单位 | 源 = 牌堆 |
|---|---|---|---|
| **抽** | — | — | 卡背从牌堆飞到手牌位；牌堆 −1、手牌 +1 |
| **上场**（`to.kind='slot'`） | ① 手牌那张**亮出来**（真的那张）→ ② 箭头：手牌 → 目标格 → ③ 卡飞进格里 → ④ 落位动画 | ① 源单位**闪光** → ② 箭头：单位 → 目标格 → ③ 新卡**直接落位**（不经过手牌，因为是效果召出来的） | — |
| **场地**（`to.kind='slot'`，挂在格上方窄槽） | ① 手牌亮出 → ② 箭头：手牌 → **格子顶部那条窄槽** → ③ 场地图标落进窄槽，**该格描边变实**（表示这一格被改造了） | 同左，源换成一个单位闪光 | — |
| **增益 / 减益**（`to.kind='unit'` 或 `'player'`） | ① 手牌亮出 → ② 箭头：手牌 → 目标 → ③ 目标身上 `+2/+2` 飘字 + 一次脉冲 → ④ 卡进弃牌堆 | ① 源单位闪光 → ② 箭头：单位 → 目标 → ③ 目标飘字 + 脉冲 | — |
| **攻击** | — | ① 箭头：源 → 目标 → ② 源 `translate` 冲到目标上方 → ③ 伤害飘字（`-3`）→ ④ 源 `translate` 移回 | — |

> 表里没写「友方/敌方」—— 因为那已经由 `to.side` 决定，**演出配方与敌我无关**：
> 「给他自己人加增益」和「给我的人加增益」是同一条配方，只是箭头终点落在不同半场。
> 这就是 §4.1 那条铁律带来的简化。

**四个演出原语**（只需要这四个就够覆盖上表全部）：

| 原语 | 干什么 | 用在哪 |
|---|---|---|
| `arrow(fromEl, toEl, color)` | 画一条箭头，短暂停留后淡出 | 上场 / 增益 / 减益 / 攻击 |

## 六、队列与锁

```js
const queue = [];
let running = false;

function push(task, meta) {              // meta 例：{ turn: 3, side: 'enemy' }
  return new Promise((resolve, reject) => {
    queue.push({ task, meta, resolve, reject });
    if (!running) run();
  });
}

async function run() {
  running = true;
  lockInput('ANIMATING');                // 锁
  while (queue.length) {
    const e = queue.shift();
    try { e.resolve(await e.task()); } catch (err) { e.reject(err); }
  }
  running = false;
  lockInput(null);
  onIdle();
}
```

**三个必须一起做的配套：**

1. **锁只有一把，带 reason**。手牌、场上单位、英雄、结束回合**全部先问锁**。文章原话：*「不要只禁用拖拽，快捷键或双击仍然能出牌」*。三个 reason：`ANIMATING`（可加速/跳过）· `RESOLVING`（不给加速）· `WAITING_REMOTE`（给"等待中"提示）。
2. **动画中不许被覆盖**。每个实体挂一个 `animating` 标记，`render()` 跳过它 —— 否则「亮牌」亮到一半就被下一条变更改掉。
3. **中断要收干净**。`pointercancel` / 页面失焦 / 弹窗 → 当前动画**直接跳到终态**（用 Web Animations API 的 `finish()`，而不是 `cancel()` 回起点），然后继续播队列。这样状态不会停在半路。

## 七、9 条逐条走通

以「敌方一个回合」为例，假设它做了这些（编号对应你列的 9 条）。

### 第 1 条 · 抽牌

- **计划**：`{kind:'draw', side:'enemy', count:1}`
- **结算**：牌堆 −1、手牌 +1
- **演出**：一张**卡背**从对手牌堆飞到手牌位（0.35s）；牌堆数字 −1。抽到的**内容不揭示**（对手的手牌是隐藏信息）

### 第 2 条 · 从手牌上场一个单位

- **计划**：`{kind:'deploy', side:'enemy', card:{...}, to:'e2'}`
- **结算**：手牌 −1、`e2` 位被占、单位加入战场
- **演出**：① 手牌区那一张**亮出正面**（停留 0.5s，玩家必须看清是哪张）→ ② 箭头：手牌 → `e2` → ③ 卡飞进 `e2` → ④ 落位

### 第 3 条 · 通过场上单位的效果上场一个单位

- **计划**：`{kind:'summon', side:'enemy', from:'e1', card:{...}, to:'e3'}`
- **结算**：`e1` 发动一次召唤效果、`e3` 被占
- **演出**：**和上一条的区别就在这里** —— ① 是 `e1` **闪光**（不是手牌亮牌）→ ② 箭头：`e1` → `e3` → ③ 新卡**直接落位**。
  玩家由此看出「这个新单位是 `e1` 召出来的，不是从手上打的」。**这一条正是「源形态决定演出」的典型例子。**

### 第 4 条 · 用手牌给**他**的单位加增益

- **计划**：`{kind:'buff', side:'enemy', source:{from:'hand', card}, target:{kind:'unit', uid:'e1'}, delta:{atk:+2, hp:+2}}`
- **结算**：手牌 −1、`e1` 的 `atk/hp` +2
- **演出**：手牌亮出 → 箭头：手牌 → `e1` → `e1` 飘 `+2/+2`（绿色）+ 脉冲 → 卡进弃牌堆

### 第 5 条 · 用手牌给**我**的单位施加减益

- **计划**：`{kind:'debuff', …, target:{kind:'unit', uid:'p1'}, delta:{atk:-2}}`
- **演出**：**和上一条是同一段** —— 只有飘字颜色与符号不同（红色 `-2`）。
  这就是为什么增益/减益**不该写成两个动作**。

### 第 6 条 · 让**他**的单位给**他**的单位加增益

- **计划**：`{kind:'buff', side:'enemy', source:{from:'unit', uid:'e1'}, target:{kind:'unit', uid:'e2'}, delta:{...}}`
- **演出**：`e1` 闪光 → 箭头：`e1` → `e2` → `e2` 飘字 + 脉冲
  （与第 4 条的区别只在**箭头从哪出发**）

### 第 7 条 · 让**他**的单位给**我**的单位减益

- 同上，出发点 `e1`、落点我方 `p1`、飘字为红。**没有任何新机制。**

### 第 8 条 · 他的单位攻击我的单位

- **计划**：`{kind:'attack', side:'enemy', source:'e1', target:{kind:'unit', uid:'p1'}}`
- **结算**：**两条伤害**（攻方也掉血，如果规则如此）、可能的退场
- **演出**：① 箭头：`e1` → `p1` → ② `e1` `translate` 冲到 `p1` 上方（0.18s）→ ③ 双方飘伤害数字 → ④ `e1` 移回
  退场用现有的「移除元素」逻辑，放在这条动画的**最后一步**（而不是 250ms 后的 `setTimeout`）

### 第 9 条 · 他的单位攻击我这个玩家

- **计划**：`{kind:'attack', …, target:{kind:'player', side:'player'}}`
- **演出**：与第 8 条**同一段配方**，只是②的位移目标是**英雄区**（`#playerhero`），③的飘字落在英雄血条上

> **小结**：9 条 → **4 个演出原语 + 1 张配方表 + 1 个队列**。
> 每条新操作将来加进来，只需在配方表里多一行，不用碰队列。

## 八、挡在路上的三件事（这一节是本文最重要的部分）

我按你的 9 条去核对了现有代码，**有三处必须先解决，否则管线做出来没东西可演**：

### 8.1 上游的 AI 只会做 9 条里的 2 条

现状（`AI.js` / `index.js`）：

| 现有能力 | 对应你列的哪条 |
|---|---|
| `computerCardPlace()`：按法力找**第一张**费用正好等于上限的牌，`appendChild` 上场 | **只有第 2 条**，而且没有「亮牌」这一步 |
| `AI()`：按场上张数分 7 个分支，用单位打人 | **第 8 / 9 条**（但目标选择与伤害写入混在各分支里） |
| — | **第 1、3、4、5、6、7 条完全不存在** |

**所以管线不能只做「包装」**：包一层拿不到「谁打了谁」这个意图（下面 8.2 会说为什么），而且另外 6 条动作现在压根没人产出。

**结论：需要一个「能产出这 9 种动作」的规划器**，取代 `AI()` 那 7 个分支。

### 8.2 为什么不能靠「比前后差异」把动作反推出来

一个看起来省事的办法是：调 `AI()` 之前快照、调完之后再快照，比对差异。
**但它只能得到「结果」，得不到「意图」**：

- 差异告诉不了你「`e1` 打了 `p1`」还是「`e1` 的效果伤了 `p1`」——**而箭头必须知道是谁干的**；
- 差异也分不出「一条动作造成 3 点」还是「三条动作各造成 1 点」——**而飘字次数要靠这个**。

`AI.js` 里那些伤害是**直接往 DOM 文本上写**的（`maxAttack.children[1].children[0].innerText = opponentHealth - alliedAttack`），
全文件没有一处统一的「造成伤害」入口可供挂钩。**这就是必须换成规划器的根本原因。**

### 8.3 卡没有「效果数据」

上游 `MinionCard` 只有 `attack / health / mana / info / name / imageString`，`info` 是一句话文案，**没有任何结构化的效果**。
真正实现了效果的只有 `card_effects.js` 里按**卡名**硬编码的几张（Lifedrinker、Alexstrasza……）。

所以第 4/5/6/7 条（增益、减益）**现在无米下锅**：即使规划器想「用手牌加个增益」，也不知道哪张牌能加、加多少。

**最小解法**（不碰上游的 `MinionCard`）：我们自己加一张效果表，按卡名索引：

```js
// 我们自己的文件，不动 deck.js
const CARD_EFFECTS = {
  'Lifedrinker':      { on: 'play',  ops: [{op:'damage', target:'enemyPlayer', value:3},
                                           {op:'heal',   target:'allyPlayer',  value:3}] },
  'Stormwind Champion':{ on: 'play', ops: [{op:'buff', target:'allAllyUnits', delta:{atk:+1, hp:+1}}] },
  'Voodoo Doctor':    { on: 'play',  ops: [{op:'heal', target:'anyUnit', value:2, choose:true}] },
  'Glacial Shard':    { on: 'play',  ops: [{op:'debuff', target:'enemyUnit', freezes:true, choose:true}] },
  // …把现有 37 张补齐；没有文案效果的牌不给条目即可
};
```

这张表同时解决三件事：规划器知道**能出什么**、结算器知道**算什么**、演出层知道**亮哪张牌**。

## 十四、v2.1 落地记录（2026-10-02 晚）

第 1 期已经落地，代码在 `关卡挑战版/src/scripts/pipeline.js`。**上面三问中的第 3 问已经不需要你点头了** —— 我找到了不动上游的做法：

**§9 原本要改上游三处，改成包装 + 拦截。** 理由是「上游一字未改」是这份 fork 的立身之本（`组装.py --check` 里有断言盯着它），而我们自己的交互层本来就掌握着"松手即结算"这个入口 —— 于是：

| 方案原计划 | 现在改为 | 结果 |
|---|---|---|
| 改 `opponentTurn()` 的调度 | 包装（第 2 期做） | 上游调度原样保留，我们只接管"什么时候播" |
| 停用 `AI()` / `computerCardPlace()` | 包装：保留它的**决策**，只对它的**结果**做叙述（第 2 期做） | 难度手感不变，`campaign.js` 的三档标定不用重做 |
| 改 `attack.js` 的结算时机 | 完全不用动：玩家攻击的入口在我们手里，把补发的 mousedown 排到"打中"那一拍即可 | 结算路径一个字没改 |

**另两处与本文不同：**

- **不建 8 个文件，只建 1 个** `pipeline.js`（按"层"分节）。原因：要压进 MMD 卡，每条正则上限 18000 UTF-16，**规则条数就是成本**。
- **加了看门狗**（本文没写）：每段动画配一个墙钟超时，到点 `finish()` 跳到终态再放行。原因是在被节流 / 后台 / iframe 降频的环境里，`Animation.finished` 由 rAF 驱动、**可能永远不来**，队列会永久卡住且锁不放。实测在这台被节流的验证浏览器里它每次都会触发（1.5 秒的演出要 8 秒走完）。

**第 1 期实测结果**（`HS_PIPELINE`）：松手 → 箭头(2ms) → 冲上去 → **结算在这一拍触发** → 飘伤害 → 移回 → 解锁，线索节点用完即清（演出层残留恒 0）；演出期间点手牌拖不起来（锁有效）；未实现的动作安静跳过；演示接口 `HS_PIPELINE.demo('attack')` 不改任何游戏状态。

**踩到一个真 bug 并已修**：锁在捕获阶段把"打中"那一拍补发的 mousedown 一起拦了 —— 箭头飞过去、伤害不生效。现在内部补发的事件带 `__hsStrike` 标记，`onDown` 放行但不参与。**凡是"我们主动制造的事件"都要能被识别出来**，这条写进了代码注释。

**下一步（第 2 期）**：敌方动作的规划器 + `draw` / `deploy` 两条配方。默认按"包装 AI、只叙述结果"做，**不动难度**。效果表（第 3 期）先做 §13.2 那 6 张。
