> 这份文件对应 `6-架构-重构第二版.md` 定的路线里**阶段 1 与阶段 2**：
> 阶段 1 建纯逻辑引擎 + 事件层 + 效果数据表 + 回归基线；阶段 2 双跑对照、产出不一致清单。

> `Math.random`，同一串命令必然得到同一个末态哈希。

## 1. 三个新件与它们的分工

| 文件 | 是什么 | 硬约束 |
|---|---|---|
| `游戏/事件.js` | 事件（叙事）+ 变更（施工图）+ 席位投影 + 稳定哈希 | 纯逻辑 |
| `游戏/引擎.js` | `reduce(状态, 命令, 环境) → {状态, 事件, 变更, 待选择}` | 纯逻辑 |
| `游戏/卡库.js` 丙段 | 效果数据表（29 张卡：攻/血/费/关键词/战吼/亡语） | **纯数据** |

"纯逻辑"是**构建期就挡住的**，不靠自觉：`工具/组装.py` 的 `pure_logic_problems()` 会扫
`游戏/引擎.js` 与 `游戏/事件.js`，出现 `document` / `window` / `Date.now` / `Math.random` /
`localStorage` / `setTimeout` 就报错（先剥注释再扫，所以注释里提到这些词不算）。
同一条约束在 `test_engine.mjs` 里**又挡了一道**（node 侧独立扫描），两道都会红。

三个概念别混（这是整套设计的地基）：

| 概念 | 是什么 | 谁在用 |
|---|---|---|
| **命令 Command** | 意图：我想做什么（`{类型:'出牌', 席位:'p0', 手牌序号, 格子}`） | 界面 / bot 产出 |
| **事件 Event** | 结果：确实发生了什么（带 `序号` / `id` / `链` / `因`，四类：规则/触发/系统/表现） | 演出层消费、日志存档 |
| **变更 Mutation** | 怎么落到状态上（`置` / `删` / `压入` / `抽出` 四种最小操作） | 状态层应用、回放 |

**变更是"施工图"，不是事后补的 diff**：引擎在草稿上改的同时把每条改动记成操作，
最后 `新状态 = 事件.应用(原状态, 变更)`。测试里有一条不变量盯着这件事 ——
每条命令都验一次「应用(原状态, 变更) 深等于 新状态」，标准对局 298 步、410 条命令，**0 次不一致**。

## 2. 规则做到哪一步（刻意划的线）

按 `6-架构-重构第二版.md` §一.5 的**第一版**做，但堆叠这一块直接做成了"真可插"：

| 机制 | 这一版做到什么 |
|---|---|
| **状态检查（SBA）** | **完整**。血量 ≤ 0 立刻进墓地、亡语立即触发、英雄归零立刻判胜负。每次移交优先权之前都跑，跑到不动为止（死亡触发亡语、亡语又可能造成死亡） |
| **优先权** | 单方行动：出牌/攻击/英雄技能**只允许本回合的主动方**，且要拿着优先权；拿不到行动权的一方只能让过 |
| **堆叠** | **LIFO、可插、可多条**。任何压栈动作之后**对手先拿到优先权** —— 这就是"可以在它生效前再插一条" |
| **结算** | 双方连续让过后结算栈顶；结算时**重新验目标**，目标在响应期间没了就**落空**（堆叠不是摆设） |
| **待选择** | 战吼等需要选目标的，引擎输出 `待选择{可选, 草稿}`，界面选完把新命令送回来。**引擎绝不自己猜玩家的选择**（只有一个合法目标时自动绑定 —— 那不是猜，是唯一解） |
| **效果四类** | 一次性 ✓ · 触发（战吼/亡语/伤害后）✓ · 关键词（嘲讽/神圣护盾/冲锋/剧毒/伤害后冻结）✓ · **静止持续（光环）与替换效果 ✗ 没做** |
| **随机** | 状态里的 `rng{种子, 游标}`，xorshift 混合。**整局可回放** |

**为什么光环没做**：上游那套卡里没有一个真光环（Stormwind Champion 在上游就是"战吼 +1/+1"，
不是持续光环）。按 `5-架构-重构探索.md` §八.D 的教训 —— **先跑通 20 张卡再抽象**，
否则就是"设计出一门用不上的语言"。真需要时再加，效果表的结构留得下（`效果[]` 里加一类"持续"即可）。

### 两个容易写反、都已经踩过的地方（写在代码注释里，也写在这）

1. **"一回合只能打一次"是宣布攻击时就付的代价，不是结算时才付。**
   写成结算时付，同一个小兵能在栈上连压十几次（每次都合法），栈永远清不完 —— 实测卡到 400 步上限、
   只走到第 4 回合。这和"付费不用堆叠"是同一条道理（出牌也是一压栈就扣法力）。
2. **伤害是同时的**：防守方哪怕被这一击打死，也照样把攻击力打回来。
   早先写成"打完还活着才反击"，于是 2 攻的 Maexxna 打死 6/7 的巨人却毫发无伤 —— 被对照清单的第 4 条抓住。

## 3. 效果表（卡库.js 丙段）

**29 张**：20 多张可打出的随从 + 5 张召唤物（Whelp / Boar / Skeleton / Murloc Scout / Slime）。

```js
'Elven Archer': { 费: 1, 攻: 1, 血: 1, 战吼: [{ 动作: '伤害', 值: 1, 目标: '任意' }] },
'Sludge Belcher': { 费: 5, 攻: 3, 血: 5, 关键词: { 嘲讽: true },
                    亡语: [{ 动作: '召唤', 卡: 'Slime', 数量: 1 }] },
```

动作覆盖：伤害 / 治疗 / 加成 / 召唤 / 抽牌 / 冻结 / 消灭。
目标口径：无 / 自身 / 自身英雄 / 自身随从 / 任意 / 任意随从 / 友方随从 / 敌方随从 / 敌方嘲讽随从 / 敌方英雄 / 敌方角色。

**数值是手抄的一份，所以被机器盯着**：`test_levels.mjs` 的 G 段逐张核对本表与上游 `deck.js` 的
（攻/血/费）—— 抄错一位、或者上游改了卡面，当场红。实测 29 张全部一致。
另外还断言"效果表确实有表达力"：七类动作、四个关键词各自至少有一张卡用到。

**为什么自己抄一份而不是读上游的卡对象**：① 引擎是纯逻辑，不许吃带 DOM 方法的 class 实例；
② 效果必须变成数据才谈得上"加卡不改引擎"（`card_effects.js` 是"直接改 DOM"的反面教材）；
③ 抄错了有机器兜着（上一条）。

## 4. 回归基线：标准对局

`工具/标准对局.json`（由 `node test_engine.mjs --基线` 生成）：

```
种子 20261003 · 双方 15 张固定牌组 · 血量 30:20 · 先手 p0
→ 298 步 · 912 条事件 · 第 31 回合分出胜负（p0 胜）
事件摘要哈希 03f4f240a26f67d5
末态哈希     6f8585b06a5a98a5
```

基线里存三样东西，每一样守着一类改动：

| 存了什么 | 守着什么 |
|---|---|
| **命令序列**（脚本 bot 走出来的 410 条） | 规则的"合法集合"变了（比如某条判定放宽了）→ bot 的决策就变了 → 当场不一致 |
| **事件摘要哈希**（`类别:类型@席位` 连成的串） | 判定的**顺序与内容**变了（伤害、死亡、触发、压栈结算的先后） |
| **末态哈希** | 状态本身变了 |

再加一条独立验证：把基线里的命令**重新放一遍**（`引擎.回放`），末态哈希必须仍然一致 ——
这条证明"命令 → 末态"是**函数关系**，不是侥幸。

脚本 bot 的策略写在测试里（不写进引擎）：有嘲讽先打嘲讽；只在"能一击换掉对方"时才交易，
换不掉就打脸；法力够就出牌；还有英雄技能。**这条策略改过一版** —— 早先"有随从就打随从"
两边会互相磨到第 39 回合还不分胜负（400 步上限跑满），换成上面这套之后第 31 回合结束。

> 有意改规则之后要重算基线：`node test_engine.mjs --基线`。**基线变了但你没打算改规则，就是踩到东西了。**

## 5. 双跑对照（阶段 2）

`node test_对照.mjs` → 生成 `工具/对照清单.md`：17 条规则，逐条写清
「老路径怎么做的（**带源码行证据**）／新引擎怎么做的（**真的跑一遍**）／判定／结论」。

**判定四档**：`一致` / `设计不同` / `上游缺陷` / `待对齐`。本次：**一致 9 · 不一致 8**。

### 为什么对照放在 node 里做

页面里的老路径是"**DOM 即状态**"（血量读 `children[1].children[0].innerText`）。想在那里连续影子跑，
得先把整套 DOM 读数接成引擎的输入 —— 那是阶段 3 的活。而现在**能逐条比对**的那些规则
（数值、判定、边界），在 node 里比对证据更硬：老路径的证据是**源码行**（可 grep 复核），
新引擎的证据是**真跑一遍**（422 项断言）。

阶段 2 在页面上已经落地的部分：`游戏/事件.js` 与 `游戏/引擎.js` **已经随页面装载**
（页面自检 ㉓ 专门确认"引擎与事件层已装载、可影子跑"）。所以"影子跑"的**底座**在页面里是齐的，
缺的是把 DOM 读数接进去。

### 不一致的每一条都有解释（抄自 `工具/对照清单.md`）

| # | 规则 | 哪一类 | 一句话结论 |
|---|---|---|---|
| 6 | 嘲讽 | **上游缺陷** | 上游 attack.js **只维护** `tauntExists`、**从不用它拦玩家的攻击**；真正读它的是 AI.js，而且条件是 `numOfOpponentCards <= 1`（只在对面只剩一张时才认嘲讽）→ 引擎按"有嘲讽必须先打嘲讽"统一 |
| 8 | 死亡移除 / 亡语 | **上游缺陷** | 老路径死亡移除写在两处；亡语是 `card_effects.js` 直接改 DOM（`style.` 27 处），而且敌方出带效果的牌时效果**根本不生效** → 引擎用数据表 + 一处 SBA 统一 |
| 9 | 效果怎么表达 | 设计不同 | 命令式改 DOM vs 效果数据表（D3/D4：先数据表，挡不住再上小 DSL） |
| 13 | 冻结 | **待对齐** | 上游只把"冻结"写在卡面文案里，没有机制；引擎已实现（伤害后冻结 + 不能攻击 + 回合结束解冻），**界面还没画冻结角标** |
| 14 | 随机 | 设计不同 | 老路径 `Math.random`（界面.js 1 处）无法复现；引擎注入种子（D4 的前提） |
| 15 | 隐藏信息 | 设计不同 | 老路径对手手牌在 `enemyHand` 数组里谁都能读；引擎两处投影（D2） |
| 16 | 优先权 / 堆叠 | 设计不同 | 老路径没有回合内响应窗口，"打中那一拍才结算"是靠**演出延后补发 mousedown**凑的观感；引擎里那是规则的自然结果 |
| 17 | 对手真手牌 | 设计不同 | 上游电脑**没有手牌**（发牌时对它是 `computerDeck.cards.shift()` 掉 3 张、直接消失；出牌时从牌库直接挑）；引擎两边都是真手牌（D12 落到规则层） |

9 条 `一致` 里，有两条值得一提：
**神圣护盾**（上游认 `children[2]`，我们给敌方侧补过空子节点）与**死亡移除**
（以前两处各写一份）—— 引擎把它们**合成了一处实现**，这正是 `9-进度-全线排查.md` 第一条说的总病根。

## 6. 阶段 3 的门槛（现在还不能拆老规则）

`对照清单.md` 里没有 `待查` 这一类（`待查` 只在测试红的时候出现）。要动手**移开冗余规则**之前，
上表每一条都要落到实处：

1. **上游缺陷那两条**（嘲讽、效果分叉）：引擎已经按正确规则做了。老路径那边要么保留（玩家继续老玩法）、
   要么改成走引擎 —— 这就是阶段 3 的主体。**改之前必须先让界面能"按游标渲染"**（把已提交但还没演的变更藏起来），

## 7. 战斗规则重定 + 两处交互修复（2026-10-03 第二轮）

用户看过画面之后提了三件事：两条是 bug，一条是把战斗机制整个换掉。**三件都落地了。**

### 7.1 交互 bug ①：瞄准期没有那条"从发起单位指向目标"的虚线

**症状**：选单位攻击时看不到瞄准线（只有选中单位本身有绿光），于是不知道自己在打谁。

**根因**（与 ② 是同一个）：上游那条红色虚线由 `attack.js` 里的一个 mousedown 处理器负责
（它 `svg.style.display='block'`，再给 `body` 挂一个跟着鼠标更新 `svgpath` 的 mousemove）——
而**那个处理器只绑给"它跑的那一刻已经在场上的卡"**（见下）。新上场的单位根本没有它，
所以既没有线、也没有"选中"这个状态。

**改法**（详见 7.2）：处理器桥接补上之后线就有了；另外**把线吸附到目标身上**：

- 指针落在某个合法目标上 → 线从**攻击方中心**画到**目标边框上朝着攻击方的那个交点**
  （箭头尖落在框边，不压进卡面）；没命中目标时保持上游原样（跟着指针，表示"还在选"）。
- 交点是**射线与矩形的进入点**（slab 法）。这个函数写过两版错的：先漏了"攻击方落在目标横向跨度内"
  （正上/正下打时最常见），再只判到"边界平面"而不是"边框线段"——
  两版都表现为箭头尖跑到卡外。现在六个方位都在页面自检 ㉕ 里断言着。

### 7.2 交互 bug ②：打敌方**随从**完全不生效（打敌方**英雄**却正常）

**根因**：上游 `attack()` 做两件事 —— ① 加 `canAttack` 绿光；②
`document.querySelectorAll('.cardinplay').forEach(e => e.addEventListener('mousedown', …))`。
② 是**一次性绑定**。我们为了治"3 点攻击打出 4 点伤害"（重复绑定 → 一次点击被处理多次）
把那具绑定体改成**只跑一次**（`wrapAttackBinding`）—— 副作用是**之后上场的卡全都没有那个处理器**。

于是：`#opposinghero` 是静态元素，第一次绑定时就在，所以在它身上结算正常；
敌方随从是后造的，我们补发的 mousedown **没人接**，于是"伤害一点没动、控制台一个字都没有"。
我方单位也一样没处理器（所以 8.1 里连瞄准线都没有）——两个症状同一个根因。

**改法**（一个字都不改上游）：装载期把 `EventTarget.prototype.addEventListener` 包一层，
**抓住**第一次绑到场上卡上的那个 mousedown 处理器 —— 它对所有卡是同一套逻辑、身份完全靠 `this` 判
（`this.classList` / `this.id`），所以任意抓到的一个都能代表全部；之后每张新卡（`syncSlots` 是唯一入口）
把同一个处理器补绑上去，绑过的打标记。
这与 `外壳.js` 换掉 `window.Audio`、包一层 `freshDeck` 是同一个套路：**改能力，不改调用点**。

⚠ 一个必须配套的细节：上游那一次绑定已经覆盖了**当下在场的卡**（通常只有两个英雄 + 英雄技能），
所以补绑前要先把它们**标记成已绑**，否则英雄会被绑两次 —— 那正是"3 点攻击打出 4 点伤害"的另一个来源。
浏览器实测：打英雄 20→18（2 点攻击只扣 2 点，没翻倍）、打随从落地并正确进墓地。

### 7.3 战斗规则重定（用户 2026-10-03）

| 旧规则 | 新规则（现在两边都照这个走） |
|---|---|
| 攻击对方单位 → 攻方**必定**挨对方的攻击力（无条件反击） | **默认没有反击**；只有目标带「反击」词条才还手 |
| 伤害是"同时"的（守方死了也照样反击） | 带「反击」时 **打完还活着才反击** |
| 攻方不付任何代价 | 攻方要付 **`攻耗`** 点生命值（红 -x）；**付到 0 就死** |
| 回合结束没有恢复 | 本回合**没攻击**的随从，在自己回合结束时回 **`恢复`** 点血（绿 +x），封顶在血上限 |

**"打完还活着才反击"为什么是正确写法**（用户在需求里点名要备注，代码里 `攻击结算` 与 `界面.js`
的补正层各写了一段）：反击是**目标的词条能力**，不是"互相同时造成的伤害"。
一个被打死的单位没有机会发动它的能力。
⚠ 这一条**推翻了上一版**：上一版按炉石"伤害同时发生"实现，还专门断言过"剧毒不免疫反伤"
（旧对照清单第 4 条）。旧断言已删，换成新的三条（默认不反击 / 反击要活着 / 攻耗能致死）。

**数据形状刻意分成两列**（`攻耗` / `恢复`）：用户明确说了"目前先攻守同值，
但之后会做成攻击耗费量和不攻击恢复量不一样的"—— 所以现在就把形状分开，之后只改数字，
不动引擎也不动界面。初始值按体量给（费 ≤2 → 1，3~5 → 2，≥6 → 3），某张卡想单独调就在那张卡上写。

**一个必须知道的直接后果**：`攻耗 ≥ 1` 时，**1 血随从一攻击就会死**
（Elven Archer / Glacial Shard / Voodoo Doctor / 各种 1/1 召唤物……）。
这是"能打空就死"＋"攻耗按体量给"的自然结果，不是 bug；不想让它们自杀就把那些卡的 `攻耗` 写成 `0`
（数据里 0 是合法的，表示"这张卡攻击不费血"）。

**界面上就是那两个数字**：贴在**血量那个数字**的上侧（红 `-x`）与下侧（绿 `+x`），下面那个会溢出卡框
（用户原话："可以溢出单位的虚线框，就像护盾那样跟随着卡牌但是不在虚线框体内"）。
⚠ 第一版把它们挂在**整张卡的**上沿/下沿，用户 2026-10-03 第二轮指出应该是"生命值这个数字的上下侧"——
现在按血量宝石（`.healthValueBackground`，`right:-5% / bottom:-9%`，尺寸 `30%×23%`）算出来的三条线对齐：
宝石中心横坐标 `right:10%`、上沿 `bottom:14%`、下沿 `bottom:-9%`。
数值由 `界面.js` 的 `挂体力徽章()` 从 **`HS_CARDS`** 取 —— 和引擎读的是同一张表，
所以界面显示的 -x/+x 与规则真正扣的血永远是同一个数。

**用户报的第二个问题：敌方不显示也不支付体力**（2026-10-03 第二轮）。根因是**卡名**：
敌方随从有两条产生路径，其中**我们自己规划器**那条（`playFromEnemyHand`）不填 `enemyNameQueue`
（那个队列是给上游 `computerCardPlace` 用的），而它紧接着**同步**调了 `syncSlots()` →
`stampName()` 从空队列里取到空串、把 `__hsName` 写死成 `''`；守卫又是"不是 undefined 就不再写"，
于是这张卡**永远认不出自己是谁** → 挂不上体力徽章、`__hs攻耗` 是 undefined → 打人时一分体力都不付。
两处修：① `playFromEnemyHand` 里我们**明明知道是哪张卡**，直接 `el.__hsName = card.name`；
② `stampName()` 改成"**没拿到名字就不落笔**"（留 undefined 等下一次同步再试）。
同时补了一条口径不一致：老路径原来只在"打随从"的分支里扣体力，**打英雄那一路不扣**，
而引擎的 `付体力` 对每次攻击都跑 —— 已对齐（打脸也要付体力，付空了照样死）。

浏览器实测（第二轮）：血量数字 cy=530，消耗徽章 cy=505（上）、恢复徽章 cy=561（下），
三者同一竖线、且不在卡片顶部；连跑几个敌方回合后，敌方随从身上带 `耗1/回1` 徽章，
Voodoo Doctor（2/1）打我英雄（30→28）之后**因为付了 1 点体力当场消失** ——
这正是"敌方不支付体力"修好的直接证据。

**老路径怎么对齐**：上游 `attack.js` 的反击是写死的（`currentAttackerHealth -= targetAttack`），
所以 `界面.js` 加了一层**临时补正**（`包我的一次攻击`）：调用上游处理器之前把目标的攻击力临时按成 0
（上游那步反伤就变成 0，同时也避免它按老算法把攻方判死而 `remove` 掉），调用之后**由我们写攻方该剩多少血**
（`攻耗` + 符合条件时的反击），并标记"攻击过"；付到 ≤0 就自己走退场叙述。
敌方那一路（`applyExchange`）同样按新规则改（否则规则就成了"只坑玩家"）。
回合结束的恢复由 `回合结束回复()` 在 `playerTurn` / `opponentTurn` 的边界上落地。
**这层补正记在对照清单里，阶段 3 一起拆掉。**

| ㉕ | 瞄准线端点落在目标边框线段上（六个方位） | 那两版几何错误（箭头尖跑到卡外/卡里） |

浏览器实测（这一轮）：㉔ 处理器已覆盖到场上每一张卡（后上场的也在）；㉕ 六个方位全部落在边框上；
打无反击的随从 → 攻方只付体力、**不挨反击**；打带反击的随从 → 活着才还手、被打死就不还手；
1 血 1 攻耗的随从打完自己消失；回合结束残血随从回满且封顶（打过的不回）；页面自检 28/28（第三轮又加了 ㉖）。

## 8. 「攻击经常不生效 + 被打的单位攻击力归零」（2026-10-03 第三轮）

用户导出「本局信息」时带出了两条症状，**同一个根因**：

- `经常出现攻击不生效`（导出的 `lastStrike` 是 `落地:false`，而 `结算时currentAttacker` 是一个
  奇怪的 `cpuCardInPlay7` —— 那是**敌方的卡 id**）；
- `进行攻击后，被攻击的对方单位的攻击力就归零了`（导出里敌方四个单位全是 `0/2` `0/4` `0/5` `0/3`）。

### 根因：`currentAttacker` 是一条会被**残留毒害**的全局量

上游判定"谁在打"**只认一个全局变量** `currentAttacker`（`attack.js` 里 `getElementById(currentAttacker)`）。
写它的只有两处：上游在选择攻方时写（`attack.js:20`）、上游在自己的**结算末尾**清（`attack.js:164`）。

后来我们把结算推迟到"箭头到达"那一拍，所以在补发 mousedown 之前要**补写回**这个变量
（`演出.js` 的 `attackRecipe`）。第一版的补写是：

```js
if (from && from.id && (W.currentAttacker === null || W.currentAttacker === undefined)) W.currentAttacker = from.id;
```

问题在于 —— **敌方攻击也走同一条配方**（`界面.js` 的 `stageAction` → `present` → `attackRecipe`），
只是它的 `onStrike` 是 `applyExchange`（我们自己的施加函数），**不会走到上游那句"结算末尾清空"**。
于是：

1. 敌方打完一次 → `currentAttacker` 被写成**那张敌方卡的 id**，而且**再也没人清它**；
2. 下一次我方攻击 → 补写看到"非空"就跳过 → 上游拿着那个**已经下场的敌方卡 id** 去 `getElementById`
   → 得到 `null` → `currentAttackerElement.children[0]` **直接抛错**；
3. 这个异常发生在**事件监听器里** —— `dispatchEvent` 不会把它冒出来，我们的 `try/catch`
   也接不到 → 表现就是**数字一点不动、控制台一个字都没有**（"经常不生效"）；
4. 而"攻击力归零"是**同一个失败的副作用**：我们的补正层在调用上游之前
   把目标的攻击力**临时按成 0**（为了让上游那步"无条件反击"变成 0），
   原来那句还原写在调用**之后** —— 上游一抛，那句就**永远执行不到**，
   于是**被攻击的那张卡的攻击力永久停在 0**。

### 修法（两处，都在我们自己的文件里）

| 修在哪 | 怎么修 |
|---|---|
| `演出.js` 的 `attackRecipe`（治根） | 补写改成**按攻方所属无条件覆盖**：攻方是玩家的东西 → 强制写回它的 id（顺手覆盖任何残留）；攻方是敌方的 → 写成 **`null`**（留着只会毒害下一次）。判"是不是敌方的"用**白名单式**写法（`opposinghero` / `computer-cardinplay`），因为英雄技能 `#playerheropower` 并不带 `player-cardinplay` 类，反过来判会把英雄技能攻击打成 null |
| `界面.js` 的 `包我的一次攻击`（治表 + 不许静默） | ① 还原放进 **`finally`** —— 上游抛不抛、目标死没死，都不会留下那个假 0；② 攻方解析不出来时**喊到控制台**（"找不到攻方，本次攻击未结算"）；③ 结算完**清空** `currentAttacker`（上游抛错时它没清成的那条路也堵上） |

### 新增自检

| # | 断言 | 挡的是什么 |
|---|---|---|
| ㉖ | 空闲时 `currentAttacker` 必须是空的 | 这条残留（它会让下一次攻击静默失效）。**赛后自检会直接红**，不必等玩家从画面上发现 |

### 浏览器实测（第三轮）

- 复现：`currentAttacker = 'cpuCardInPlay999'`（一个不存在的敌方卡 id，正是残留的形状）→
  走真实三步交互 → **攻击落地**（目标 7→5）、攻方只付 1 点体力、**被攻击方的攻击力仍是 6**、
  `结算时currentAttacker` 已经是 `null`。老代码在这一步会是"数值不动 + 目标攻击力变 0"。
- 另一半：直接补发"打中那一拍"并故意留一个不存在的攻方 id → 上游**确实**抛（血量不动），
  但**被攻击方的攻击力被还原成 6**，而且控制台留下
  `[攻击补正] 找不到攻方，本次攻击未结算。currentAttacker=cpuCardInPlay999，目标=cpuCardInPlay1` ——
  **失败不再静默**。
- 页面自检 28/28（新增 ㉖）。

### 这一轮记下的教训

**把状态寄存在"别人的全局量"里，就必须保证它不会残留。**
`currentAttacker` 是上游的，我们只是借用；借用的规矩是——
**用完要还、用前要覆盖**，而且"用前要覆盖"必须**按我们自己的语义**判断（这里是"攻方属于哪一侧"），
不能写成"它空着我才写"。第一版就是后者：把"我以为它一定是空的"当成了前提。
这与 `4.12`（把同步结算改异步，就输给了浏览器补发的那次 click）是同一类错误 ——
**只要时序变了，所有"依赖别人先/后跑"的隐式前提都要重新审一遍。**

## 9. 攻击结算收回自己手里（2026-10-03 第四轮 · 落实 D3「抛弃上游」）

用户看完第三轮的结论后点了一句：**「不是说了要抛弃原上游代码的影响，全面使用我们自主的规划器吗」**。
说得对 —— 第三轮我修的是**上游那个 `currentAttacker` 残留**（打补丁），而那个坑的**根**是：
攻击结算还在上游手里（`attack.js` 的处理器 + `currentAttacker` + DOM 即状态）。
这一轮把它整个收回来。

### 之前：一次玩家攻击要绕上游一圈

```
拖/点我方单位 → onUp → present({verb:'attack'}) → 演出播到"打中"那一拍
  → 补发一次**合成的 mousedown** 到目标 → 上游 attack.js 的处理器结算（读 DOM、写 DOM、无条件反击）
```
这条链上我们吃过三类坑（全都由"结算在别人手里"派生）：
1. **处理器只绑给"当初在场的卡"**（后上场的打不着 → 打敌方随从静默无效）；
2. **`currentAttacker` 会被残留**（敌方攻击的演出也走同一条配方，却不会走到上游"结算末尾清空"那句）
   → 下一次我方攻击在上游抛错 → **静默不生效**；
3. **上游是无条件反击**，我们只能"先把目标攻击力临时按成 0、调用后再还原" → 上游一抛错，
   那句还原就永远执行不到 → **被攻击方的攻击力永久停在 0**。

### 现在：结算完全是我们自己的

新增 `界面.js` 的 **`应用一次攻击(攻方El, 目标El, kind)`**（外层作用域），
玩家打、敌方打**走同一个函数**（原来敌方那份 `applyExchange` 已经并进来删掉）。
规则以**引擎**为准（`游戏/引擎.js` 的 `攻击结算`），一次调用按顺序做五件事：

| # | 做什么 | 与引擎的对应 |
|---|---|---|
| ① | 攻方的攻击力打到目标；目标有神圣护盾 → 吸收一次、护盾破掉 | `伤害()` 原语 |
| ② | 攻方关键词生效：**剧毒**（被伤到的随从直接销毁）、**伤害后冻结**（被伤到的角色冻结） | 关键词在伤害原语里读 |
| ③ | **默认没有反击**；目标带「反击」且**挨完还活着**才还手（攻方有护盾则吃掉这次反击） | `攻击结算` 的第③步 |
| ④ | 攻方付 `攻耗`（体力），标记"本回合攻击过" | `付体力()` |
| ⑤ | 归零的单位移除（走我们自己的退场叙述）；英雄归零 → 胜/负 | 状态检查(SBA) |

顺带把两个**一直没人实现**的关键词补上了（上游只写在卡面文案里，全线排查 3.6）：
**剧毒**与**伤害后冻结** —— 以前只有引擎有，现在页面上也真的会发生。

### 同时拔掉的三个"上游入口"

| 拔掉什么 | 为什么 |
|---|---|
| **不再补发合成 mousedown** | 那是"请上游来结算"的唯一动作。不补发，就不需要"让这一拍穿过演出锁"（`e.__hsStrike` 那条路也一并作废） |
| **`演出.js` 的"补写回 `currentAttacker`"整段删掉** | 没有上游结算在读了。㉖ 顺势变成"空闲时它必须是空的"这条哨兵 |
| **"补正层"`包我的一次攻击` 整段删掉** | 把目标攻击力按成 0 再还原那套 hack，连同它带来的"假 0"一起消失 |
| **处理器桥接（`bridgeCardBindings`/`bindAllCards`）整段退役** | 那套是为了"让后上场的卡也能被上游结算"；现在不需要上游结算了。㉔ 相应改成"攻击结算是我们自己的" |

另外在 `onDown` 的**捕获阶段**加了两道闸，把上游的结算入口彻底堵死：
- 落在**敌方目标**（`.computer-cardinplay` / `#opposinghero`）上的 mousedown 一律吃掉 ——
  否则只要 `currentAttacker` 非空，上游就会在敌方卡上自己结算一次（两条结算路径同时活着）；
- 落在**我方可攻击单位**上的 mousedown 也吃掉 —— 免得上游又去写 `currentAttacker`、又挂一条永不摘除的
  `body` mousemove 闭包。

### 顺手补的一个洞：我方失败

上游那套是 `alert("You've Lost!") + location.reload()`（粗糙，而且卡里不该弹 alert）。
**结算收回自己手里之后，"血到 0" 就不再有人接管了** —— 不补上游戏会一直跑下去。
所以加了 `我方失败()`：一条居中的小结算条（"你输了 / 重打本关 / 关卡列表"），
与关卡层那条"通关"按钮栏对称。这正是 `9-进度-全线排查.md` 里记的 ⚠「英雄归零判胜负 ——
敌方侧没有失败那条路，待补」。

### 边界（这一轮之后，上游 `attack.js` 还剩什么用）

只剩一件：`attack()` 每回合给场上卡加 **`canAttack` 绿光**（我们靠这个类判断"这个单位本轮能不能打"）。
它的选择/瞄准/结算三条路我们都不再走 —— 瞄准线是我们自己画的（`snapAimLine`），
结算走 `应用一次攻击`。**英雄技能（2 费打 1）那条路也一起静默了**（它本来就被界面隐藏）。

### 浏览器实测（第四轮）

| 用例 | 结果 |
|---|---|
| 打无反击的随从 | 守 7→5、**攻方只付 1 点体力**（2→1）、被攻击方攻击力保持 6 ✓ |
| 打带「反击」且活下来的 | 守 5→3 还手 3 → 攻方 2-1-3 = -2 **当场消失** ✓ |
| 打敌方英雄 | 英雄 20→18、攻方 5→4（付体力）、`currentAttacker` **全程为 null** ✓ |
| 打死带「反击」的 | 守方被一击带走 → **不还手**，攻方只付 3 点体力 ✓ |

四条都走**真实三步交互**（点单位 → 移到目标 → 松手），`lastStrike` 全部 `落地:true`；
页面自检 **28/28**。

### 这一轮的教训（与 §8 那条是一体的）

**"借用别人的状态"这件事，只要还借，就迟早会被它的残留咬到。**
第三轮我选择"补写它、清空它"，第四轮正确的做法是**不再借** ——
结算一旦是自己的，`currentAttacker`、合成的 mousedown、"把别人的数值改成 0"、
"给新卡补绑处理器"这一整套依附关系同时消失。
判据很简单：**如果一个 bug 的根因在"别人写的状态"上，那修法通常不是把它擦干净，而是别再依赖它。**
