## 1. 这是什么

一个能直接跑的**炉石式**卡牌对战：随从上场、下回合才能攻击、法力水晶每回合 +1、英雄技能 2 费打 1、把对手英雄打到 0 血获胜。

**战斗规则（用户 2026-10-03 重定，与炉石不同，界面上看得见）**：

- 每个单位血量**上方**有一个红色 `-x` = 执行攻击时要**消耗**的生命值（**付到 0 就死**）；
  **下方**一个绿色 `+x` = 本回合**没攻击**、回合结束时可以**恢复**的生命值（最多回满）。
- 攻击对方单位**默认不会挨反击** —— 只有目标带「**反击**」词条才还手，而且**打完还活着才反击**
  （被打死就不还手）。整个卡表里带反击的是 `Maexxna` / `The Black Knight` / `Sludge Belcher` 三张。
- 两个数字都是**可调的数据**（`游戏/卡库.js` 的效果表里 `攻耗`/`恢复` 两列），
  初始值按体量给：费 ≤2 → 1，3~5 → 2，≥6 → 3；某张卡想单独调就直接在那张卡上写。
  ⚠ 因此 **1 血的随从一攻击就会死**（攻耗 ≥ 1）—— 这是"能打空就死"的直接后果；
  不想让它们自杀，把那些卡的 `攻耗` 写成 `0`（数据里 0 合法，表示"攻击不费血"）。

在这之上加了五关阶梯：

| 关卡 | 对手 | 血量（你 : 对手） | AI 档位 | 玩家牌组 |
|---|---|---|---|---|
| 第一关 · 热身赛 | 学徒 · 血牙 | 30 : 20 | 新手 | 基础组 |
| 第二关 · 排位赛 | 老兵 · 霜牙 | 30 : 25 | 熟练 | 基础组 |
| 第三关 · 挑战赛 | 法师 · 冰喉 | 30 : 30 | 熟练 | 完整组（解锁传说卡） |
| 第四关 · 晋级赛 | 死亡骑士 · 骨语 | 30 : 35 | 大师 | 完整组 |
| 第五关 · 冠军赛 | 巫妖王 | 30 : 40 | 大师 | 完整组 |

**AI 三档的差别是真差别，不是数值缩放**：

- **新手** —— 出牌从「出得起的里面随便挑一张」，并且有一半的回合整回合不出手。
- **熟练** —— 上游原样：按法力曲线出牌（找费用正好等于当前法力上限的那张），出手时按场上张数分支挑目标。
- **大师** —— 出牌从「出得起的里面挑**费用最高**的那张」，每一步都往场上压最大的牌；从不发呆。

进度存在浏览器本机（`localStorage` 键 `hsw_campaign_v1`），**逐关解锁**：第一关永远能打，第 N 关要第 N-1 关通关。主菜单里有「清空进度」。

## 2. 怎么跑

```bash
cd 关卡挑战版
python 工具/启动.py            # 起在 8642 端口并打开浏览器
python 工具/启动.py 9000       # 换个端口
python 工具/启动.py --no-open  # 只起服务
```

不需要 `npm install`、不需要构建、**没有任何后端**。上游本来就是纯静态页面，`工具/启动.py` 只是发文件。

**目录长这样**（阶段 0 收拢、阶段 1/2 加了引擎之后）：

```
关卡挑战版/
├─ 说明/          1-怎么跑（本文件）· 2/3 设计 · 4/5/6 架构 · 7/8/9 进度 · 10 引擎与对照
├─ 游戏/          ★ 我们自己的运行时 —— 打包进 MMD 卡时**只带这个目录**
│   ├─ 外壳.js      去炉石化（静音/去卡图/开场清理）+ 关卡层（列表/进度/AI 档位/通关）
│   ├─ 事件.js      ★ 事件（叙事）+ 变更（施工图）+ 席位投影 + 稳定哈希   —— 纯逻辑
│   ├─ 引擎.js      ★ reduce(状态, 命令, 环境)：状态检查 / 优先权 / 可插堆叠 / 结算 —— 纯逻辑

│   └─ 样式.css     压平炉石素材 + 简洁窗体
├─ 工具/          组装.py（构建期校验，含"引擎不许碰 DOM"）· 启动.py · 备份.py
```

> 想直接用 `file://` 打开 `index.html` 也可以，但部分浏览器会拦本地相对资源、音频自动播放也更严，所以推荐起个静态服务。

**进去之后**：开场那道「点击继续」门槛会被自动点掉（`外壳.js skipStartupGate`），直接落到
**我们自己的主页面**（上游那个 Play / Tutorial / Shop 菜单整块不显示），三块：

| 入口 | 干什么 |
|---|---|
| **卡牌图鉴** | 列出 `HS_CARDS` 里全部卡：费用 / 攻击 / 生命 / 词条 / 说明。数值与规则**同源**（引擎读同一张表） |
| **开始游戏** | **挑战关**：五关，**格数逐关 +1**（第一关双方各 1 格 …… 第五关 5 格），按进度解锁<br>**自由关**：双方各 **1 / 3 / 5 格**三档，任选一档直接开打（不记进度） |

想直达某一局，地址栏加参数即可（自动跳过门槛并直接进对局）：

```
http://127.0.0.1:8642/?level=1     # 挑战关第一关（1 格）… ?level=5（5 格）
http://127.0.0.1:8642/?free=3      # 自由关，双方各 3 格（?free=1 / ?free=5 同理）
```

**「导出本局信息」在哪**：在局内的**设置**里（右上角设置 → 抽屉里那颗按钮）。
以前它挂在右栏的「任务区」，用户要求挪进设置；任务区现在就是**任务**的家（显示法力上限 + 任务清单）。

## 3. 与上游的差异（全部差异，逐条可查）

### 3.1 我们的运行时：`游戏/` 九个文件

阶段 0（2026-10-03）把原来散在 `src/scripts/` 的自研文件**合并、改名、搬进 `游戏/`**，
并定下「打包只带 `游戏/`」的边界。合并的规矩是**少而大**（要压进 MMD 卡时每条正则 ≤ 18000 UTF-16，
**文件数就是成本**），但**加载位次一个字没动** —— 谁在前谁在后仍然是硬要求，见下表下方的顺序。
阶段 1 又新增两个纯逻辑文件（`事件.js` / `引擎.js`）。

| 文件 | 由谁合并而来 | 职责 |
|---|---|---|
| `游戏/外壳.js` | `strip.js` + `campaign.js` | 甲段**行为**：静音（`window.Audio` 换空壳）、去卡图（包一层 `freshDeck` 清掉 `imageString`）、开场清理；乙段**关卡层**：关卡列表 UI、进度存档、AI 分档、通关结算 —— 详见 §3.4 |
| `游戏/事件.js` | **新写**（阶段 1） | 事件（叙事，四类：规则/触发/系统/表现）+ 变更（施工图，四种最小操作）+ 席位投影 + 稳定哈希。**纯逻辑** |
| `游戏/引擎.js` | **新写**（阶段 1） | `reduce(状态, 命令, 环境) → {状态, 事件, 变更, 待选择}`：状态检查 / 优先权 / 可插堆叠 / 结算。**纯逻辑** |
| `游戏/卡库.js` | `levels.js` + `campaign-pre.js` + **效果表（新）** | 甲段关卡表 + 牌组构建器（**不碰上游任何东西**，只提供数据）；乙段读 `?level=N`，在 `index.js` 跑之前把牌组与血量换成本关的；丙段**效果数据表**（29 张卡）—— 详见 §4.1 / §4.2 / 新文件 `10-架构-引擎与对照.md` |
| `游戏/资源.js` | **新写**（阶段 C） | **资源与回合**：法力上限 / 法力 / 回合号 / 抽牌补偿 + 任务驱动的上限 ±1。`W.mana`/`W.manaCapacity` 只是它写出来的缓存（唯一写入点）。**加载位次是硬要求：`index.js` 之后、`演出.js` 之前** —— 它要换掉上游的 `playerTurn`/`placeCardFunc`，而 界面.js 的回合叙述必须包到它 |
| `游戏/决策.js` | **新写**（阶段 E） | **敌方决策**：三档难度（新手随机/发呆 · 熟练=上游原样 · 大师挑最贵的可出牌、攻击优先拆最狠的）。**纯函数**（吃"费用/攻力/血量/嘲讽/是不是英雄"描述符，不碰 DOM），随机源可注入 → node 里直接测。上游 `AI.js`（51,930 UTF-16）已出列，这一份只有 3,969 |
| `游戏/演出.js` | `pipeline.js` | **演出管线**：一把带 reason 的锁 + 串行队列 + 五个演出原语 + 配方表 —— 详见 §3.8 |
| `游戏/界面.js` | `interact.js` | **交互与舞台**：固定比例画布、部署位（**格数由关卡决定**：挑战关 1→5、自由关 1/3/5）、拖手牌/拖单位、预览侧栏、两个视角的开关 —— 详见 §3.6 / §3.7 |
| `游戏/样式.css` | `ours.css` | **外观**：压平上游全部炉石素材引用 + 我们自己的简洁窗体。由 `index.html` 在 `<head>` 里加载 —— 详见 §3.4 / §3.5 |

**加载位次（`index.html` 里的先后，不能反）**：

```
游戏/外壳.js → 游戏/事件.js → 游戏/引擎.js → 游戏/卡库.js → index.js
→ … → 游戏/资源.js → 游戏/决策.js → 游戏/演出.js → 游戏/界面.js
```

（阶段 C 加了 `游戏/资源.js`、阶段 E 加了 `游戏/决策.js`，两者的位次原因：
资源层要换掉上游的 `playerTurn` / `placeCardFunc`，必须在 `index.js` **之后**；
而 界面.js 的回合叙述要包到它、敌方规划要读决策层，所以两者都必须在 界面.js **之前**。）

**页面上还剩几个上游文件**（阶段 F 第一块之后）：`styles.css` · `src/scripts/attack.js` ·
`index.js` · `src/scripts/elementsController.js`（外加 `index.html` 骨架）。
已出列：`AI.js` / `card_effects.js` / `fireworks.js` / `preventInspectElement.js`（阶段 E）与
`src/stylesheets/animations.css`（阶段 F；两个界面动效已由 `游戏/样式.css` 用自己的 keyframes 实现）。

三条硬约束的来源：
- **外壳.js 要在最前**：甲段得赶在 `index.js`/`AI.js` 造 `Audio` 之前、也赶在 卡库.js 抓 `freshDeck` 之前；
  乙段（关卡层）的副作用全部推迟到 `DOMContentLoaded`，所以它提前加载也不会读到还没挂上的数据。
- **事件.js 要在 引擎.js 之前**：引擎在**装载时**就取事件层，取不到会直接抛错（宁可在装载时报，
  也别等到第一次 reduce 才炸）。
- **卡库.js 要在 `index.js` 前**：甲段要抓到**已被包装过**的 `freshDeck`；乙段要赶在 `startGame()` 之前换牌组。

`游戏/事件.js` 与 `游戏/引擎.js` 是**纯逻辑**：不碰 DOM、不用全局时钟、不用 `Math.random`。
这条约束由 `工具/组装.py` 在**构建期**挡住（出现那六个标识符就报错），`test_engine.mjs` 里还有独立一道。
好处是它们能直接在 node 里裸跑 —— 于是"同一串命令 → 同一个末态哈希"是真的可验，而不是"一般情况成立"。

### 3.2 改了一个文件：`index.html`，1 行 `<link>` + 6 行 `<script>` + 摘掉影片那一行

我们的资源都带**内容版本号**（`?v=<内容哈希前 8 位>`），改了就自动变 —— 实测踩过"改了却像没改"（真机上表现为诡异的"伤害不生效"，其实是宿主缓存了旧脚本）。版本号由 `工具/组装.py` 从这几个文件的内容算出，不需要谁记得手动 +1。

```diff
  <script src="src/scripts/testing.js"></script>
```

外加一处替换 —— 开场影片那一行摘掉（影片文件不随包分发，留着只会每次加载白 404 一次）：

```diff
-   <source src="src/media/introcinematic.mp4" type="video/mp4">
```

跑 `python 工具/组装.py --check` 会验证：4 个标签在位、顺序正确，**且除这几行外 `index.html` 与上游逐字节一致**，同时 `index.js` / `deck.js` / `styles.css` / `AI.js` / `attack.js` / `elementsController.js` **一字未改**。

### 3.3 为什么用「包装」而不是「就地改写」

上游是 5 万行的全局脚本（`AI.js` 52 KB、`elementsController.js` 48 KB，全是顶层 `function`）。直接编辑它有两个问题：一是「这份 fork 与上游差在哪」会变得说不清；二是上游一更新就没法对齐。

所以关卡层只做两件事：**加文件**、**包装函数**。

```js
// 出牌：包装 computerCardPlace（出哪张牌）
// 出手：包装 AI（打谁、打不打）
// 通关：包装 gameWon（记进度、给「下一关」）
```

包装层整份删掉，上游照样能跑 —— 这就是「只加不改」的验收标准。

### 3.4 移除所有音频 + 去除所有卡图（2026-10-02）

**文件层面**：`组装.py` 会删掉这几个目录，共 **101 个文件 / 45.6 MB**：

| 目录 | 内容 | 文件数 | 体积 |
|---|---|---:|---:|
| `src/ost/` | 背景音乐 | 8 | 36.4 MB |
| `src/sounds/` | 音效（含 `cardPlaceSnds/`、`effectSnds/` 两个子目录） | 49 | 3.1 MB |
| `src/voiceovers/` | 语音 | 7 | 0.8 MB |
| `src/cards/` | **卡图** | 37 | 5.3 MB |
| `src/images/` | **牌桌背景 / 英雄立绘 / 卡背 / 卡包 / 状态角标** | 19 | 8.0 MB |
| `src/hints/` | **拖牌提示动画**（3 个 GIF） | 3 | 14.7 MB |
| `src/cursor/` | 自定义光标 | 4 | 0.01 MB |
| `src/fonts/` | **Belwe** —— 暴雪的商用字体 | 1 | 0.04 MB |

剥完 **`src/` 下只剩 `scripts/` 与 `stylesheets/`**，总共 **128 个文件 / 71.2 MB**。
`组装.py --check` 会验证这件事（多了任何一个目录都算失败）。

`src/media/`（开场影片）也在剥离清单里，但本次没有镜像它（`镜像上游资源.py` 已跳过），所以本地本来就没有 —— 一并记着是为了下次直接从上游整包组装时不漏。

**这段的起因**（用户 2026-10-02 的原话）：*「移除现有的代码中，关于炉石传说的开幕问候，炉石传说的开场动画，炉石传说的场景背景等，将这些炉石传说的美术素材移除，保留简洁窗体，留待我们讨论和更新属于我们的 ui 配布和动画动效。」*

**代码层面一行没删**。上游在 4 个文件里到处 `new Audio(...)`（`load.js` 第 1 行就有），
挨个删这些行等于改动上游 —— 所以 `外壳.js` 改的是**能力**，不是调用点：

```js
window.Audio = SilentMedia;                       // 所有 new Audio(src) 拿到空壳
HTMLMediaElement.prototype.play = () => Promise.resolve();   // <video> 也不出声
window.freshDeck = 包一层（把每张卡的 imageString 清成 1×1 透明图）
```

于是 `deck.js` 里那三处 `backgroundImage = url(imageString)` 自然就没有图了，
而 `deck.js` 一个字没动。

**为什么卡图要这么绕**：上游把卡图写在 `imageString` 上、由 `deck.js` 直接塞进
`style.backgroundImage`。用透明图而不是空串，是为了不产生 `url('')` 这种会去请求页面自身的地址。

**加载顺序是硬要求**：`外壳.js` 必须排在 `卡库.js` **之前** —— `卡库.js` 在加载时会把
当时的 `freshDeck` 存下来（`UPSTREAM_FRESHDECK`），如果它抓到的是未包装版本，卡图会被装回去。
`test_campaign.mjs` 的 E 段有一条专门的断言守着这个顺序。

**开场问候与开场动画**（不只是删文件）：

- **「Click anywhere to continue」那道门槛**：它本来是绕浏览器自动播放限制用的（要先有点击手势才能出声）。我们已经没有音频，门槛只剩挡路 —— `外壳.js` 替玩家点掉它（`SKIP_STARTUP_GATE`）。

|---|---|---|

| 手牌 / 法力条 / 右栏 / 预览 / 箭头 / 蒙版 | 屏幕坐标系，不参与倾斜 | 同左 |

实测（设计坐标，画布 1208×570）：立体视角下敌方那排落在 x 208–886 / y 210–260，我方那排 x 152–926 / y 305–370，敌将框 x 444–764 / y 9–145 —— 顶部正好空出 **210px** 给桌子对面的敌将。近排底边距手牌区上沿 32px。**平铺视角与改动前逐项一致**（同一组量测值完全重合，零回归）。

**为什么没有用 three.js（用户给的那个参考文件用的）**：

1. 这个页面要能离线跑、将来还要压进 MMD 卡（每条正则 ≤ 18000 UTF-16）。three.js 压缩后约 600–650 KB，**光它就要多出三十几条规则**，而我们整个游戏目前才十几条 —— 为一个视角把可打包性搭进去不划算。那个参考文件是从 `unpkg.com` 拉 three.js 的，离线直接白屏。
2. 战场本来就是 DOM：卡是 DOM、落格按矩形判定、拖放走 `elementFromPoint`。换 WebGL 等于把渲染、拾取、动画、拖放全部重写，而这套刚稳定下来。
3. 这个透视 **CSS 3D 就能做**，而且浏览器的命中测试仍然按真实投影走 —— 实测倾斜后 5 个槽、场上卡的矩形互不重叠，直角坐标判定照旧返回正确索引。

所以：**视角 == 一组 CSS 变换与位置变量**，`界面.js` 里只有一个 `setView()`。

### 3.8 演出管线（第 1 期已落地）

设计见 `设计/演出动画管线-方案-v2.md`；这里是它的第 1 期实现，文件是 `游戏/演出.js`。

**做出来的东西**（全部实测过）：

| 件 | 说明 | 实测结果 |
|---|---|---|
| **一把带 reason 的锁** | `ANIMATING` / `RESOLVING` / `WAITING`；演出中在 `document` **捕获阶段**吃掉 mousedown，所以上游那些绑在卡片上的处理器也进不来 | 演出中点手牌 → 状态仍是 `idle`（拖不起来） |
| **串行队列** | `push()` 返回 Promise，一条播完才走下一条；空下来自动解锁并通知 | `stats()` 全程 `queued/running/inflight` 归零 |
| **四个演出原语** | 箭头（描边生长 + 三角浮现）· 运卡 · 冲刺（冲出去/移回来分两段）· 飘数字（伤害/治疗/增益/减益四色） | 逐个跑过，线索节点用完即清，演出层残留恒为 0 |
| **配方表** | `(源形态 × 动作) → 一段演出`，第 1 期只填了 `attack` | 未实现的动作（如 `summon`）**安静跳过**，不打断队列 |
| **看门狗** | 每段动画配一个墙钟超时，到点 `finish()` 跳到终态再放行 | 这台被节流的浏览器里**真的会触发**（一段 1.5 秒的演出要 8 秒才走完），没有它队列会永久卡死、锁永远不放 |

**玩法上的变化**：玩家拖场上单位去攻击，现在是「箭头 → 冲上去 → **这一拍才补发上游的 mousedown** → 飘伤害 → 移回」。结算路径一个字没改，只是"什么时候按下去"归我们排 —— 所以数字与打击同时出现，而不是先掉血再飞过去。Esc / 右键可以跳过（跳到终态，不是回起点）。

**击中玩家（英雄）有专属特效**（用户 2026-10-02 要的）：打单位只是"两个棋子碰一下"，打英雄多一圈暖色**冲击环** + 英雄框**震一下**，分量不一样。配方表按 `to.kind` 自动选，不用调用方说。

**不能攻击的单位会被拦下并给出反馈**：上游判定"能不能打"的唯一标志是 `canAttack`（它的 `attack()` 在我方回合开始时加上），**不能打的时候它把这次点击静默忽略** —— 不扣血、不报错。而我们原来会照常起手、箭头飞过去、冲刺、飘数字，最后什么都没有。见 §4.11。现在这种单位点下去是**红框 + 抖一下**，不再起手。

**结算自查**：`HS_PIPELINE.lastStrike()` 能读出最近一次攻击"有没有落地"（补发前后的血量快照逐项对比）。**只记录、不重试** —— 万一是写到了别处，重试会造成二次伤害。

**与方案的两处不同（都是我改的，理由写在代码里）**：

1. **不改上游，改用包装 + 拦截。** 方案 §9 原本要改上游三处。但「上游一字未改」是这份 fork 的立身之本（`组装.py --check` 里有断言盯着），而我们自己的交互层本来就掌着"松手即结算"这个入口 —— 所以改成：结算照旧交给上游，我们只接管**什么时候播什么**。
2. **一个文件，不是方案里列的 8 个。** 这套东西最终要压进 MMD 卡，每条正则上限 18000 UTF-16，**规则条数就是成本**：8 个文件 = 8 条规则起步，而这几层之间只通过几个函数打交道。

### 3.9 预览面板的两种用法 + 瞄准线的交棒（2026-10-02）

| 什么时候 | 显示什么 | 数据从哪来 |
|---|---|---|
| 拖手牌时 | 名字 / 费用 / 攻血 / 效果文案 | 手牌 DOM 里是完整卡面 → `readCard()` |
| **悬停场上卡牌或英雄时** | 名字 / 攻血（英雄只显示血） | **场上卡只剩攻血两个数字**（卡面在去卡图那轮被清空），名字得自己记 |

**名字怎么记**（`stampName`）：我方的在上场前我们刚设过 `getNameOfElement`；敌方的用**牌堆差集** —— 上游从 `computerDeck.cards` 取牌，打出去的那张会从数组里消失，差集就能认出是哪一张（实测认出了 AI 出的 `Slime`）。认不出就退化成「我方单位 / 对方单位」，不影响出牌。英雄的名字直接读上游那两个 name 标签，所以立体视角下敌将搬到桌子对面时，名字和血量都跟着走。

⚠ 必须是整层 `display:none`，不能只清路径 —— 上游那次选择给 `body` 挂了一个**永不摘除**的 mousemove 闭包，玩家一动鼠标它就把虚线重新画出来（实测确认过）。而 `clearAimLine` **不碰 `currentAttacker`**：那是结算的唯一依据，演出期间必须留着（见 §4.12）。

**还没做**：敌方那 9 条动作的**规划器**（`draw` / `deploy` / `summon` / `buff` / `debuff` 的配方是空的）。敌方现在仍是上游 `AI()` 那套 `setTimeout` 流程，所以**看不到过程，只有结果**——这正是下一步。

## 4. 关键实现点（踩过的坑）

### 4.1 牌组的切分是硬编码下标，而且下标 30 被跳过

上游 `startGame()` 里：

```js
playerDeck   = new Deck(deck.cards.slice(0, 30))
computerDeck = new Deck(deck.cards.slice(31, 60))   // ← 下标 30 没人要
```

所以关卡牌组必须是 `[30 张玩家牌] + [1 张占位] + [29 张对手牌] + [召唤物]`。`卡库.js` 按这个格式生成，`test_levels.mjs` 里有断言守着长度与各段归属。

### 4.2 血量写 10 会被上游当成教程

上游 `startGame()` 用「对手血是不是 10」来嗅探教程模式：

```js
if (document.querySelector('.opposingHeroHealth').innerText == 10) isTutorial = true;
```

所以**关卡表里对手血量不能是 10**，否则整关会掉进教程分支。`test_levels.mjs` 有一条专门的断言拦住它。

### 4.3 `freshDeck` 必须先抓住再覆盖（否则无限递归）

`deck.js` 的 `class Deck { constructor(cards = freshDeck()) }` 是按标识符解析的，所以覆盖 `window.freshDeck` 就能换牌组。但**覆盖后的函数不能再回头调 `window.freshDeck`** —— 那就是自己调自己。

`卡库.js` 在加载时先把上游那份存下来（`UPSTREAM_FRESHDECK`），之后一律用存下来的那份。

### 4.4 上游有一张卡是死数据

`deck.js` 里定义了 `Bloodfen Raptor`（`bloodfen_raptor`），但**从来没把它放进返回的牌组数组**。按卡名索引取不到它。

这不是我们引入的问题，是上游的。`卡库.js` 的 `fill()` 遇到不认识的卡名会**当场抛错**（而不是静默出一套残牌组）—— 第一次跑测试就是被这条抓出来的。关卡表里已经换成真正能上场的卡。

### 4.5 换关靠整页重载，不靠原地重开

`index.js` 在解析到末尾时就 `startGame()` 发牌，所以想换牌组只能赶在它之前动手。原地重开一局要清理一堆脚本作用域的全局状态（`manaCapacity`、`oldNumOfChild`、已绑的 `mousedown`、场上残留节点），清不干净就会串局。

所以：**选关 → 整页重载到 `?level=N` → `卡库.js（乙段）` 在 `index.js` 之前换牌组与血量**。代价只是重载一次。

---

### 4.6 一个全屏空 div 能让所有命中测试**静默**失效

上游 `index.html` 有个 `<div id="load"></div>`。`load.js` 在 `readyState === 'complete'` 之后才把它设成 `visibility:hidden; opacity:0`（还带 0.5s 过渡）。这条依赖两头都脆：它是**晚注册**的 `onreadystatechange`；而且过渡没跑完时，计算值仍停在 `visible`。

它是**全屏 + `z-index:1000000` + `pointer-events:auto`** 的。只要它还 visible，`document.elementFromPoint(x, y)` 就**永远返回它** —— 症状是"所有悬停命中一起失灵"，而且**完全不报错**：拿到的是一个合法元素，只是不是你要的那个（我们的悬停高亮就是这么丢的）。

所以两头都改：① `游戏/样式.css` 里 `#load { display: none !important }`（它本来就是个空 div，上游的意图也是藏掉它）；② 交互层不再单靠 `elementFromPoint`，而是先按候选目标的矩形做几何命中。

### 4.7 上游会在回合中途改 `#endturn` 的行内 z-index

`index.js:191` 把它抬到 **50**，`elementsController.js` 里还有 21 / 10 / 9 一串。我们那层预览原本是 31 —— 于是**我方的回合**（正好是玩家拖牌的时候）那颗按钮会画在预览上面。

教训：和上游抢层叠时，不能拿"平时量到的值"当依据（安静时它是 2、还是行内的），要看它**最高能到多少**。

### 4.8 百分比外边距是按「父元素**宽度**」解析的

上游用 `margin-top: 93%` 这种写法把攻/血徽章摆到卡片下角。百分比外边距解析的是 **containing block 的宽度**，不是高度 —— 在 150×200 的竖卡上勉强对得上；卡片一改成 251:207（150×124），`93% × 150 = 139px` 直接把徽章顶到卡外面去（实测攻徽章落在卡下方 11px、血徽章探出下沿 41px）。

徽章里那个数字（`.attackValue`）同样是按卡片尺寸算的 `bottom/right` 百分比，跟着偏了 20px。两处都改成 `left/right/bottom` 的百分比（左右按宽、上下按高）与 `50% + translate(-50%,-50%)` 居中，从此与卡片比例无关。血量那颗宝石保留了它自己的 `rotate(-45deg)`，数字反向转 `45deg` 保持正立。

### 4.9 立体视角连带出来的三条硬约束

倾斜一加，三个"以前对、现在错"的地方就暴露了：

1. **落格坐标不能量屏幕矩形。** 卡片是写 `el.style.left` 落进格子的，而 `cellLeft()` 原来是拿 `getBoundingClientRect` 量相邻两格的屏幕距离再除以缩放 —— 棋盘一 `rotateX`，量到的是**投影后压扁的距离**，卡片会一格一格往里挤。`offsetLeft` 是布局值，与 transform 无关，换成它才对。
2. **箭头必须活在屏幕坐标系里。** `#hs-arrow` 原来挂在 `#game` 里、用设计坐标画：倾斜之后设计坐标到屏幕不再是线性缩放，箭头就指不到指针底下了。改成挂在 `body` 上、`position: fixed`、直接用 `clientX/clientY`（和上游那条红色虚线同一套），两个视角都不用再管。同理，"指针在哪半边"这类判断（预览放哪侧、蒙版盖哪半）改用**归一化屏幕位置**，不再用设计坐标。
3. **手牌、右栏、法力条不能跟着倒。** 所以战场必须先被包进一个独立图层（`#hs-table`），倾斜只施加在它身上。新元素一定要记得加进右栏那个共同选择器组（`#hs-settings / #hs-view / #hs-quest`）—— 那组里才有 `position: absolute`，漏了就会掉到 (0,0)。

另外记一条**验图环境**的坑（不是产品问题，但反复误导过判断）：这台内置浏览器被节流，**CSS 过渡几乎不推进**，`setView` 之后立刻量到的是过渡起点，看上去"类名加上了但几何没变"。验图前先注入 `#game * { transition: none !important; animation: none !important }`，量到的才是终态。

### 4.10 自己的锁把自己的结算锁死了

第 1 期接上之后，"攻击"这个动作在真局里**箭头飞过去、数字不出现、伤害不生效**。

原因很隐蔽：锁是在 `document` 的**捕获阶段**吃掉 mousedown 的（这是故意的，好让上游那些绑在元素上的处理器也进不来）。而演出里"打中"这一拍，恰恰是靠**补发一次 mousedown** 去触发上游那套结算的 —— 于是它被自己的锁拦在了捕获阶段，永远到不了目标自己的处理器。**自己把自己锁住。**

改法：给这一拍在事件对象上打个标记（`e.__hsStrike`），`onDown` 见到它就**放行但不参与**（它要送到目标自己的处理器才算数，而它不是一次新的操作）。

教训：**锁和"内部补发的事件"必须走两条路**。凡是"我们主动制造的事件"都要能被识别出来，否则以后每加一处内部派发，都会踩同一个坑。

### 4.11 「伤害不生效」的真根因：上游对"不能攻击"的点击是**静默忽略**

症状：箭头飞过去、冲上去、数字飘出来，**血量一点没动**，控制台一个字都没有。

查证过程（都没能复现，于是回头读上游）：我先把两个方向都实测通了 —— 单位打敌将（20→18，扣血 `-2` 也正常显示）、单位互殴（4→2 / 5→2），全程无报错。既然复现不了，就去读上游 `attack.js` 的判定：

- 能不能攻击的**唯一**标志是 `canAttack`（`attack()` 在我方回合开始时加，等于"召唤延迟"）；
- 不能攻击时，那次 mousedown 走不进任何分支 —— **什么都不做，也不报错**；
- 而**刚上场的单位本轮本来就不能攻击**，所以"刚放下去就打"必然踩到这一条。

我们原来对攻击方**不做任何校验**，于是照常起手、照常演出一整套 —— 演出结束、伤害为零。这正是"伤害不生效"的来源，而且它是**一直存在**的（不是我这一轮引入的），只是有了演出之后才显得刺眼。

改法：起手前检查 `canAttack`，不能打就**红框 + 抖一下**，不进入瞄准态。

顺带记两个同类的坑：
- **上游对非法点击一律静默**。凡是"上游会静默忽略"的操作，我们这一层都要提前校验并给反馈，否则玩家只会觉得游戏坏了。
- **Python 的隐式字符串拼接**：改多行字面量时如果只替换第一行，剩下那半截会被默默接在后面。这次就是这样把 `index.html` 的注释改坏了 —— 是 `组装.py --check` 抓出来的（那道检查值回票价）。

### 4.12 「所有攻击都不生效」：把同步结算推后，就输给了浏览器补发的那次 click

这是**我自己引入的回归**，也是这一轮最难查的一个 —— 记下来，因为它是"同一类"问题的第三个样本。

**症状**：任何视角、任何目标（打英雄、打单位）全都不生效，而且一点动静都没有。

**链条**（四步，缺一步都解释不通）：

1. 真实鼠标攻击时，`mousedown` 落在**单位**上、`mouseup` 落在**目标**上 —— 元素不同，
   浏览器就会在两者的**公共祖先**（这里是 `#game`）补发一次 `click`。
2. 我们那一层的 `onClick` 看到 target 不在白名单里，就调 `cancelAim()`，而它会写
   `currentAttacker = null`。
3. 上游判定"谁在打"**只认 `currentAttacker`** 这一个全局量。以前结算是**同步**的
   （就在 mouseup 里补发那次 mousedown），赶得在第 2 步之前；而我为了做"箭头 → 冲上去 →
   打中那一拍才结算"的演出，把结算**推迟了约 1.5 秒** —— 于是第 2 步先跑，
   结算时"攻击方不见了"，上游什么都不做、也不报错。
4. 表现就是**每一次攻击都静默不生效**。

**为什么自动测试一直是绿的**：合成的 `dispatchEvent` **不会**产生浏览器派生的事件
（`click` 就是派生出来的）。我的测试全是合成事件，所以从来没跑进第 1 步 ——
**测试的盲点不在断言，而在场景**：要复现真实交互，必须把派生事件一起补上。
（复现脚本里手动补一次 `click` 给公共祖先，症状立刻重现：`currentAttacker` 松手时是 `tA`，
补发 click 后变成 `null`，`落地: false`。）

**改法（两层，都要）**：

- `onClick` 在演出期间**不取消**（`isLocked()` 直接返回）—— 治本；
- 结算前若 `currentAttacker` 已被清空，**补写回**这次攻击的单位 —— 兜底，
  因为上游自己也会在结算后的 `setTimeout` 里清它。

**顺带修掉的第二个隐患**：结算抛错时我原来用 `try/catch` 把它**吞了**，
于是 `lastStrike()` 只显示"没变化" —— 界面表现和"被静默忽略"一模一样，
等于我亲手把最关键的线索藏了起来。现在异常会被记录下来（`lastStrike().报错`）
并打到控制台。

**教训**：**把一段同步逻辑改成异步，等于把它和"事件循环里其它已经排好的东西"的先后顺序
重新洗牌。** 凡是依赖"我比别人先跑"的隐式前提（这里是上游那套"点一次就走完"的假设），
都要在改异步时重新审一遍。
