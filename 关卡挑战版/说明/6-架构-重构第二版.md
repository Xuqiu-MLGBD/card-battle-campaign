## 一、堆叠 / 优先权 / 状态检查（通俗版）

这三样是万智牌式"响应"能力的来源。先讲清各自是什么，再说我们该做多深。

### 1. 状态检查（SBA）：**不容置疑的自动核查**

- **一句话**：任何时候，只要场上存在"该发生的事"，它**立刻发生**，不需要任何人同意、也不需要排队。
- **例子**：某个单位血量 ≤ 0 → 立刻死、进坟场；某个光环不再生效 → 立刻失去加成。
- **关键**：它**不看谁在等、不等人点确认**。每次有人要做事之前，都先跑一遍。
- **我们已经有的雏形**：现在"血量到 0 就 `remove()`"就是一条 SBA（只是散在几处、且两边各写一份 —— 见 `全线排查-问题清单.md` 第一条）。

### 2. 优先权：**这一刻谁有权行动**

- **一句话**：任何时刻只有一个"持有优先权"的人能行动。他可以**做事**（出牌/发动效果），也可以**让过**。
- **推进规则**：所有人都连续让过 → 进入下一步（阶段/回合结束）。
- **例子**：我宣布"结束回合"（= 让过）→ 对手也可以让过（那就真结束）或**响应**（先做一件事）→ 响应完优先权回来，再问我要不要让过。
- **我们已经有的雏形**：现在是"我方回合 / 敌方回合"两个大块，没有"让过/响应"的窗口。

### 3. 堆叠：**待办事项的栈**

- **一句话**：所有"已经发动、但还没生效"的东西，按**后进先出**排成一摞，双方都有机会在它生效前再插一条。
- **例子**：我打出"造成 3 点伤害" → 它**先进堆叠、不立刻生效** → 你响应一张"给他 +0/+2" → 结算顺序：先 +2 生效，再 3 点伤害 → 于是他没死。
- **没有堆叠会怎样**：回合变成"一人一口气做完"，响应、连锁、心理博弈全部不存在。

### 4. 三者如何轮流（引擎里的主循环）

```
① 状态检查(SBA)        ← 有该发生的事立刻发生（死亡/光环失效/胜负）
② 若堆叠非空 → 给"优先权持有者"：
      做事（新对象压在栈顶，回到 ①） 或 让过
   双方都让过 → 结算栈顶那一项 → 回到 ①
③ 堆叠空了且都让过 → 推进阶段/回合 → 回到 ①
```

### 5. 我的建议：**分两版做**（这是你要拍板的"规则深度"）

| 版本 | 内容 | 能做到什么 | 工作量 |
|---|---|---|---|
| **第一版（建议先做）** | **状态检查（完整）+ 单方优先权**（谁该动就谁动，没有响应窗口）+ 堆叠只装"一条动作" | 规则正确、顺序清晰、事件链完整；"打中那一拍才结算"就是它的自然结果 | 小 |
| **第二版** | 堆叠**真正可插**（响应/连锁）+ 双方优先权循环 | 万智牌味道：响应、打断、上钩 | 中大 |

**关键**：第一版就要把**堆叠这个数据结构留在状态里**（哪怕只装一条），第二版才能扩，不用返工。
（我们现在的"演出队列"是**表现层**的队列，和规则层的堆叠不是一回事 —— 别合并。）

## 二、效果语言（你问的第 4 件事）

### 1. 问题本身是什么

"卡的效果"要怎么写，才能既**表达力够**（万智牌那样）、又**不用改引擎代码**？

- **做法 A：数据表**（每张卡一行，交给通用执行器）
  ```js
  { 名:'巫妖王之怒', 触发:'打出时', 目标:'敌方英雄', 动作:[{类型:'伤害', 值:3}] }
  ```
- **做法 B：小 DSL**（自己造一门小语言）
  ```
  when played: deal 3 damage to 敌方英雄; if 目标死亡 then draw 1
  ```
  引擎里有个解释器读它。表达力强得多，但要写解释器（约 200 行）并保证它**封闭**（不用 `eval`）。

### 2. 我的建议：**先 A，后 B，并且按"打包进卡"来选型**

- **先数据表**：常见效果（伤害/治疗/加成/召唤/抽牌/冻结）约 20 张卡就能覆盖，**纯数据、打包友好、调试直观**；
- **等表撑不住再上 DSL**：过度早做的就是"设计出一门用不上的语言"；
- **两者共存**：引擎先认数据表；将来加 DSL 时，把它编译成同一张表（这样引擎只认一种输入 ✓）。

### 3. 如果要进 `/mmd` 卡里，额外硬约束（**这些直接决定目录形状**）

| # | 约束 | 对设计的后果 |
|---|---|---|
| M1 | **打包按"条"计**：每条正则 ≤ 18000 UTF-16 | **文件要少而大** —— 千万不要把模块拆成一堆小文件（这会同时解决你"找不到文件"的问题） |
| M2 | **零网络** | 所有资源内联/数据 URI；字体用系统字体；**不许 CDN**（我们已经是 ✓） |
| M3 | **沙盒怪癖** | `styleSheets/cssRules` 访问受限（自检已改行为检查 ✓）、剪贴板不可用（导出用文本框 ✓）、定时器可能被节流（看门狗 ✓）—— 继续遵守，别再加依赖这些的功能 |
| M4 | **存档两套** | 独立网页 → `localStorage`；卡里 → SDK 存档。做**存储适配器**，一套代码两种后端 |
| M5 | **切屏/iframe 重载要能续** | 事件溯源 + 快照天然满足（状态 = 初始 + 事件序列） |
| M6 | **首屏要快** | 数据和引擎要小；卡库**只带本局要用的**（别把全部卡塞进包） |
| M7 | **一份代码两个壳** | 差异只在"壳"：存储、SDK 调用、尺寸适配。引擎与演出**完全共用** |

**一句话结论**：效果语言选型不重要，**"为打包设计"才重要** —— 少文件、纯数据、零网络、可续存。
