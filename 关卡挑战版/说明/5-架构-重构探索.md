## 〇、先说一个概念上的补丁（最重要的一条）

你的第七条模块说：「在动画播放完成之后，把对应的事件加载到状态记录中」。

**这一条我建议改掉**，理由是它会让你自己定的第 4 条规则（"不要让动画反过来影响规则"）失效：

- 一旦"状态"由动画播完才提交，那么**跳过动画 / 加速 / 断线重连**都会改变状态的推进时机 —— 规则就依赖表现了；
- 正确的关系是：**状态永远是真相，且立刻提交；动画只是"播到哪了"的一个游标**。

```
命令 → 引擎计算 → ① 状态立刻提交（权威）  ←→  ② 动画拿事件去播，游标 lastPlayedSeq 缓慢推进
                                                      ↑ 界面渲染 = f(状态, 游标)：把"还没演到"的部分先藏起来
```

好处：跳过/加速 = 游标往前跳 ✓；断线重连 = 游标直接拉到最新 ✓；**规则从不看动画** ✓。
代价：界面要能"按游标渲染"（把已提交但还没演的变更**藏起来**，我们的"牌先隐形、撞击那一拍才现身"就是这个机制 ✓）。

**术语上再加一个概念**（你的两条已经分清"命令=意图 / 事件=已发生"，还缺第三个）：

| 概念 | 是什么 | 谁用 |
|---|---|---|
| **命令 Command** | 意图：我想做什么 | 界面 / bot 产出 |
| **事件 Event** | 结果：确实发生了什么（不可变、带顺序号与因果） | 动画消费、日志存档 |
| **变更 Mutation / Diff** | **怎么落到状态上**（可重放的最小操作集） | 状态层应用、回放 |

事件是"叙事"，变更是"施工图"。两者都挂在同一条链上：`chainId` 相同 = 同一个命令的后果。

## 一、命令与事件（你的模块一）

**你要求的**：所有状态变化都产生事件；事件有顺序号；事件带因果；命令是意图、事件是结果；界面只发命令；动画只消费事件。—— 全都对，我全部接住。

**要补的**：

1. **事务边界**：一个命令 → 引擎一次产出 `{ state', events[], mutations[], pendingChoice? }`，**要么整批成立、要么整批拒绝**。合法性验证失败时产出一个"被拒绝事件"（也入日志 ✓ 便于排查"我明明点了却没反应"）。
2. **事件分四类**（只有前三类影响状态）：
   - `rules`：规则事件（伤害/死亡/抽牌…）
   - `triggered`：由规则事件派生出来的触发（"因为受伤，所以触发 X"）
   - `system`：回合/阶段/优先权/堆叠
   - `fx`：**纯表现**（飘字、镜头）—— 这一类的存在是为了**绝不让表现混进规则**
3. **因果与链**：`event.cause = parentEventId`、`event.chain = chainId`。你举的例子"因为 A 攻击 B，所以 B 受到伤害"就是 `damage.cause = attackEvent.id`。
4. **两层时间**：逻辑时间（`turn / phase / step / seq`）+ 真实时间戳。**排序只用逻辑时间**，时间戳只给人看。
5. **投影（隐藏信息）**：事件里可能含隐藏信息（对手抽到什么牌）。所以**同一条事件流要能按"视角"投影**：`project(events, seat)` —— 界面与 bot 只看自己那份。单机也要这么做，否则将来做联机要重写。
6. **幂等**：事件带唯一 id，重复应用同一条事件不改变状态（重连时常发生）。

## 二、核心引擎（你的模块二）

**你要求的**：合法性验证、按状态算结果、输出事件、判费用/目标/能否出牌、处理回合/阶段/优先权/堆叠、处理伤害/死亡/抽牌/弃牌、纯逻辑不碰界面、输入(状态+命令)输出(新状态+事件+待玩家选择)、可保存回放测试、随机带种子。—— 全都对。

**要补的**（这些决定"能不能做到万智牌那样"）：

1. **纯函数的硬约束**：引擎内**不许出现** `document` / `window` / `Date.now` / `Math.random`。
   → 建议**用构建期检查直接禁掉**（`组装.py` 里加一条：engine 目录出现这些标识符就报错）。这条能省掉将来无数"跑一次变一次"的诡异 bug。
2. **随机注入**：`rng` 作为参数传入（种子存进存档 ✓），洗牌/随机目标都用它。
3. **选择（Choice）是一等公民**：目标选择、弃牌选择、是否响应、付费方式…… 引擎输出 `pendingChoice`，界面把它变成一个界面操作，再把玩家的**新命令**送回来。**引擎绝不自己"猜"玩家的选择**。
4. **堆叠 + 优先权 + 状态检查**：这是 MTG 味道的核心。建议结构：
   ```
   状态检查(SBA) → 若堆叠非空 → 逐次移交优先权 → 都让过 → 结算栈顶 → 回到状态检查
   状态检查在**每次移交优先权之前**跑（死亡/传奇规则/光环失效都在这里发生）
   ```
5. **四类效果**（先做这四类，不做完整 613 层）：
   - **一次性效果**（"打击 3 点"）
   - **静止/持续效果**（"你的其他单位 +1/+1"）—— 需要**层与时间戳**的最简版（先只做"攻防修正"一类）
   - **触发效果**（"当 X 时，Y"）
   - **替换效果**（"如果会怎样，改成…"）—— 最容易漏、也最影响手感的一类
6. **可测**：状态必须是**纯 JSON**（可 `JSON.stringify` 往返）；提供 `hash(state)`；**保存一份"标准对局"**（命令序列 + 期望事件序列 + 末态哈希）作为回归基线。
7. **引擎不知道 UI 的存在**，也不知道动画的存在 —— 它只认得"状态 + 命令"。

## 三、状态记录（你的模块三）

**你要求的**：给引擎提供计算数据；切屏/关闭会话后可继续。—— 对。

**要补的**：

1. **单一真相源 + 双份持久化**：`快照(低频) + 事件日志(全量)`。加载 = 最近快照 + 重放剩余事件。
2. **版本与迁移**：存档带 `schemaVersion`；升级时写 `migrate(state)`。否则"改动一次就玩不了老存档"。
3. **写入时机**：**每条命令链结束时**存一次 + 页面 `visibilitychange` 时补一次（切屏/关闭 ✓）。**绝不在链中间存**（会存下半截状态）。
4. **与现有 localStorage 的关系**：现在存的是关卡进度（`hsw_campaign_v1`）与视角（`hsw_view_v1`），**要分开键**，别混进对局存档。
5. **容量**：事件日志要设上限（比如最近 500 条）+ 定期压成快照；否则 localStorage 会满。

## 四、动画播放（你的模块四）

**你要求的**：把规则事件演出来（抽牌/出牌/施放/结算/攻击/阻挡/伤害/死亡/进坟场）；支持并行、阻塞、跳过、加速；只读事件；按顺序播；决策时追到当前状态；断线重连跳到最新；规则不等动画。—— 全对，而且**我们现在的 `演出.js` 已经是大半个了**（锁 / 串行队列 / 六个原语 / 配方表 / `whenIdle` / 看门狗 / 倍速 / 跳过）。

**要补的**：

1. **事件 → 动画的映射表 + 兜底**：未知事件用"默认动画"（例如目标闪一下 + 一句提示）——**新增机制永远不会让播放器卡住**。
2. **每条动画声明 `blocking`**（是否阻塞后续）→ 于是"并行组"= 一组不阻塞的动画同拍起播 ✓（你要求的"支持并行"落地方式）。
3. **时长预算**：一条链总时长超预算（比如 4 秒）就自动提速 —— 万智牌式的链动辄十几步，不设预算玩家会烦。
4. **游标与追赶**：动画持有 `lastPlayedSeq`。断线/重连/跳过 = 把游标推到目标 seq，**该藏的先藏、直接到位**。
5. **动画只能"通知播放完毕"**，**绝不回写规则**（§〇 那条的落地形式）。

## 五、回合时钟 / 事件总线 / 验收（你的模块五）

**你要求的**：承载引擎输出的事件串、验收动画、并在动画完成后把事件加载进状态。—— 前两条对，第三条按 §〇 改成"状态立即提交 + 游标"，理由已述。

**要补的**：时钟其实是**总调度器**，它拥有唯一的循环：

```
while (true):
  cmd = 等下一个命令（界面 / bot / 超时）
  r = engine.reduce(state, cmd)
  if r.rejected: 播一个"被拒绝"提示; continue
  state = commit(state, r.mutations)      // 立刻，权威
  events.push(r.events)
  animator.play(r.events)                 // 不等它也行；要等就在这儿 await
  if r.pendingChoice: 交给界面/bot 生成下一个命令
```

另外两件：**超时/无操作**（玩家不响应也要能推进回合 ✓）与**阶段推进的规则**（谁在什么时候拿到优先权）。

## 六、界面加载与渲染（你的模块六）

**你要求的**：让玩家能轻松地产生命令。—— 对，补两条硬约束：

1. **渲染是纯函数**：`render(view(state, seat, cursor))`，**DOM 里不存状态**。
   ⚠ 这一条与我们现在的做法相反：**上游是把 DOM 当状态**（读 `children[1].children[0].innerHTML` 当血量）。迁移的**最大工作量就在这**。
2. **界面只发命令**：点击/拖拽 → 构造 `Command` → 交给时钟。**绝不"点击 → 直接扣血 → 播动画"**（正是你在模块二里点名要避免的）。
3. 选择类交互（选目标/弃牌/是否响应）由 `pendingChoice` 驱动，界面**只画"现在能选什么"**。

## 七、bot 逻辑（你的模块七）

**要补的**（bot 在这一套里其实最简单，因为它的接口和界面一样）：

1. **bot = 命令生成器**：`bot(view(state, seat)) → Command[]`，与界面走完全同一套接口。
2. **难度 = 策略质量，不是作弊**：新手=合法的里随便挑（且有机会发呆）；熟练=贪心（按价值/曲线）；大师=1~2 层前瞻（带时间预算）。
3. **可复现**：bot 的随机也走注入的 `rng(seed)` → 整局可回放。
4. **不许偷看隐藏信息**（除非你明确要"大师会算牌"，那要写进设计并让玩家知道）。

## 十一、需要你拍板的五个问题

1. **规则深度**：真做「堆叠 + 优先权 + 状态检查」（万智牌味道 ✓ 复杂度高），还是先做「回合 → 主要阶段 → 结束」的简化版？
2. **隐藏信息**：对手手牌**真的隐藏**吗？（决定引擎是否一开始就做席位投影）
3. **上游的地位**：保留它做**渲染**（我们接管规则）、还是连渲染也逐步自研？（后者前期慢，但长期干净）
4. **效果语言**：先**数据表**（20 张卡跑通）还是直接上**小 DSL**？
5. **要不要"双跑对照期"**？（我强烈建议要：它是唯一能保证"不改坏现有东西"的手段）

## 十二、成本与风险的实话

- **不是小工程**：规则层要重写（约 1000~1500 行 + 测试），但**演出层与界面层大部分能留**；
- **最大风险**：上游"DOM 即状态"（读界面文本算血量）。**这是迁移的难点，也是收益最大的地方**——一旦状态独立，回合/堆叠/隐藏信息/回放才谈得上；
- **最容易翻车的地方**：一口气把效果做到万智牌级。建议按 §十 的节奏、每阶段可回退；
- **保护措施**：每阶段快照 + 老路径保留开关 + 双跑对照 + 标准对局基线。
